# Photo retouch

The method a photographer and an agent arrived at over two studio projects (portraits and a team shoot), correction by correction. The method (classical tools, references measured with the same code, iteration to tolerance) applies to any photo. The code in the templates was validated on studio portraits on a grey seamless wall (Fujifilm X-Trans RAF, flash); for any other kind of photo, see Which branch > Other photos.

Projects live in one root folder, `$PHOTO_ROOT` (default `~/PHOTOS`), one folder per project: `<date>-<name>/`. The working code to start from is in [templates/](templates/README.md); how the result was reached, for humans, is [HISTORY.md](HISTORY.md).

## The bar

Every rule below came from one of the photographer's corrections, and keeps its reason beside it. Where none applies, the bar is that the result looks **hand-edited** in front of the camera original.

- **Classical tools only.** Inpainting, frequency separation, curves, gains and alpha matting: every pixel comes from the photo itself. Detection models (face, skin) may locate things; no model writes a pixel (Gemini, Flux, gpt-image, GFPGAN and CodeFormer included). The photographer forbade generative AI on 2026-10-10.
- **From the RAW.** Every edit starts from the RAW develop. The camera JPEG is a target or a QA reference only. When the brief says "no JPG", the project root carries the marker file `.sin-jpg` and no JPEG exists at any step, previews included. [scripts/photo_guard.py](scripts/photo_guard.py) enforces it (setup: [references/guard.md](references/guard.md)).
- **Native resolution, maximum quality.** Never upsample. Exports have no quality option.
- **Contours identical to the camera original.** No bite, rim, halo, veil or disc where the wall meets skin, hair, lashes or clothing.
- **Pimples go, freckles and moles stay.** Eyes, brows, mouth and nostrils are protected zones.
- **Private.** Photos and edits stay on the machine: never a notes vault, git or a third-party service.

## What the photographer reads

The photographer reads the images, not the process (said on 2026-10-15). Every word of method in a reply is time and usage they pay for and skip. Before reading any image or launching a subagent, read [references/speed.md](references/speed.md) > Agent time.

- **A reply is the result in 1–3 lines** plus the file to look at in `editadas/`. No method, measurements, step list or "what I tried" unless asked why or what was touched.
- **Process images are browsed alone** in Finder's gallery: name the folder in the reply, and don't open them for the photographer or describe them one by one.
- **Ask only when the decision is theirs**: the brief (step 0), taste, which reference or version wins, touching an approved master, the delivery folder, the neutral to white-balance from, installing the guard hook, and stopping one of their processes. Everything else, decide and do.

## Where things go

The folder names are Spanish because the templates use them: `editadas/` deliverables, `proceso/` process images, `proceso-notas/` notes and numbers, `respaldos/` regression baselines, `originales/` read-only RAWs, `work/` regenerable scratch.

- Every **image that shows what was done** goes straight into `proceso/`, named `<group>-<name>` (`process_file` in `templates/portrait-qa/recipe/output.py`): side-by-side comparisons, masks, alpha and trimaps, dE maps, histograms, numbered candidates, grids, measurement sheets, whole versions. `proceso/` holds images only and **no subfolders**, since Finder's gallery doesn't open them (asked on 2026-10-15, with everything except plain zooms). The pipeline tools still write `proceso/<group>/` subfolders: when copying `templates/pipeline/`, port `process_file` into `recipe/common.py` and turn every path under `PROCESS` that has a subfolder into `process_file("<group>", name)` (`grep -n 'PROCESS /' tools recipe`: most bind it to a constant like `OUT`, some nest two levels). A single crop with nothing drawn and nothing beside it goes to `work/`. Numbers, notes and data arrays go to `proceso-notas/`, grouped in subfolders by the same group names. 659 images were once stranded in `work/` and `/tmp`, where macOS deleted some.
- Paths like `tools/`, `recipe/` and `recipe/photos.py` are the project's, once `templates/pipeline/` is copied into it.
- A script that is run again (a measurement, a regression check) lives in `tools/`, a pipeline step in `recipe/`, a one-off in `proceso-notas/`. Never in `work/`, which is regenerable: a script left there is rebuilt by the next agent who can't find it.
- Decisions made by eye (spots, kept marks, protected zones, wall marks) are written by hand into `recipe/photos.py`. A decision inferred at run time drifts between runs and reopens approved spots.
- The project README is the **handoff**, kept complete for the next agent, in the photographer's language, with these sections: the brief (step 0); what was touched, one table per style (`Qué se tocó en cada estilo` in a Spanish README); the pending list (`Pendiente`); a dated change log (practices.md > Every change (step 6)); deliveries.

## Which branch

In an existing project, read its README first. A change to existing code or to an approved master follows [references/practices.md](references/practices.md) > Every change.

- **New photos** → step 0, then copy `templates/pipeline/` into the project and set it up per [templates/README.md](templates/README.md) > How to start, instead of rebuilding tools (the second project rebuilt 16 tools where 7 existed). The QA tools the steps name are in `templates/portrait-qa/`, written for square avatars: port each one, with the `recipe/` modules it imports, when its step comes up (module names collide with `pipeline/recipe/`, so merge, never overwrite). The template carries `.sin-jpg`: keep it only if the brief says no JPG. Then steps 1 to 8 in order; with existing styles, step 4 measures their references against the new photos before iterating.
- **Other photos** (outdoors, colored or busy backgrounds, products, no faces, another camera) → the same steps, using the parts of the templates that don't assume a studio wall: develop (rawpy reads any RAW, see templates/README.md > How to start, step 1; an iPhone ProRAW DNG arrives already demosaiced and linear, so it only needs white balance and tone), measurement, iteration and QA. Skip what doesn't exist in the photo (the face inventory with no faces, the wall steps with no seamless wall): the tolerance rows and Done-when clauses that name skin, a face or the wall apply only where one exists, Frame clipping and the gradual-corrections gate apply to every photo, and `wall` in `recipe/photos.py` holds the patches of the confirmed neutral. Where no number is left for what the request changes, the bar's hand-edited test decides. In the templates those are calls inside the scripts: with no seamless wall, leave `wall_marks` empty and skip `neutral_stains` and, with no black clothing, the three lint calls in `recipe/retouch.py`; with no faces, `"faces": []` is required. With no seamless wall or no faces, use `np.ones(img.shape[:2], np.float32)` for `evening_gain` in `recipe/grade.py` and `tools/color_check.py`: it evens the wall toward the light at the faces, and with no faces it returns NaN. Set grade.py's `EXPOSURE`, `CURVE`, `CHROMA` and `SKIN_HUE` per session (templates/README.md > How to start, step 3); `SKIN_HUE` also turns wood. In the step 0 message, ask which neutral to white-balance from, and name the untested parts in one line.
- **A change to an existing project** → by kind: a spot, mole, wall mark, lint or under-eye zone change goes to its step 2 verdict in `recipe/photos.py` and step 3, then steps 6 to 8; a light, color or style change, or an under-eye strength (one face's `under_eye.light` and `under_eye.color` in `recipe/photos.py`, every face's `INTENSITY`: [references/skin.md](references/skin.md)), goes to steps 5 to 8. Either way, scoped to the photo × style the change touches. A request that names no project or photo means the project the session is in; with none, ask which.
- **A reference style or look to match** (the photographer sends a photo whose look they want) → step 4 with that photo first, then steps 5 to 8.
- **An export or a delivery** of existing masters → no render and no audit; files from `editadas/` per [references/delivery.md](references/delivery.md) > Exports. Done when the files are written and the README's deliveries section has a dated line with the files, format, size and folder. If another agent is working in the project (a process of theirs shows in `pgrep -fl` for that project, or `find <project> -type f -mmin -10` lists a file), put that line in your reply instead of editing the README.
- **A plain question** ("is everything saved", "show me") → answer from the files directly, with no audit. "Saved" means the editor's versions are in `editadas/versiones.json` ([references/editor.md](references/editor.md) > Versions), the masters are in `editadas/`, and nothing of the project lives only in `work/` or `/tmp`.
- **"What did you touch"** → the README's what-was-touched table, one yes/no line per row for the style asked (matched on its key or its name in `STYLES` of `recipe/styles.py`), in the README's language, never merged. If the table is missing, build it first (a README write: with another agent in the project, as in the export branch, give the table in the reply instead) with these rows: exposure, blacks, whites, shadows, highlights, contrast, clarity, WB, saturation, hue, sharpening, NR, grain, vignette, local D&B, blemishes, wall, crop.
- **Build or change the editor** → [references/editor.md](references/editor.md).

## Any agent

The skill works the same in any harness and at any effort; what changes is what enforces it.

- **Unless `photo_guard.py` is registered as a hook** (Claude Code only, setup: [references/guard.md](references/guard.md)), check the guard's two rules before every write: nothing of the project in `/tmp`, and no JPEG where `.sin-jpg` exists.
- **Without subagents**, run the mechanical steps inline, with outputs through `| tail`.

## Steps

Do the steps one at a time and check each "Done when" before the next. Where [references/measurement.md](references/measurement.md) > Tolerances or [references/qa.md](references/qa.md) gives a number, the number decides, not a guess about taste.

0. **Brief.** Ask what the photos are for and for 1–3 photos of how the photographer wants them to look: links or files, any photo whose look they like. They can skip it; then step 4 finds references and they pick. Ask once, in one message, together with whether the project must have no JPEG.
   Done when the README holds the use, the references given (or "find them") and the JPEG decision.
1. **Develop** to the linear float base (`work/<photo>-base.tif`, float16, values over 1 kept), with white balance from a confirmed neutral (in the studio, the wall).
   Done when clipped pixels are under 0.005 % (hot pixels only) and the count is in `proceso-notas/`. Count them where the develop is still 16-bit integers, since the float base can't show a clip: in the template, on the `raw.postprocess` output inside `develop.py`'s `demosaic()`, in its first call, the one with the wall white balance (LibRaw clips at 65535 there), `100 * np.mean((rgb >= 65535).any(axis=-1))`. `develop.py` doesn't print it. If the sensor itself clipped past that bar (`raw.raw_image_visible >= raw.white_level`), no develop passes: count it, flag it for the photographer in the reply and the pending list, and go on; it is not a failed gate. When the graded master clips (Frame clipping in measurement.md > Tolerances), the lever is `EXPOSURE` in `recipe/grade.py`; the editor's exposure can't bring back what the 16-bit master clipped.
2. **Inventory** at 100–200 % with coordinate grids. Faces: one candidate sheet per face (`recipe/spots.py`), each candidate called heal (pimple, red mark, scratch) or keep (mole, freckle, scar) one by one, plus the protected zones (eyes, brows, mouth, nostrils) and, when the brief includes under-eyes, the lower lash lines. Wall: one mark sheet per photo (`recipe/wall.py`), each mark called heal or keep, with its real center and size from `tools/wall_measure.py`. Automatic detection failed on the first face it met.
   Done when every candidate called heal is in `recipe/photos.py` (`spots`, `wall_marks`), every kept face candidate is in `kept`, every face has its `features` (and `lids` when the brief includes under-eyes), and the sheets are in `proceso/`.
3. **Retouch**: details in [references/skin.md](references/skin.md). For wall and light, prefer smooth global gains without a mask. When a mask is unavoidable, follow [references/compositing.md](references/compositing.md).
   Done when every candidate called heal shows healed (skin: `tools/compare.py ... --diff` crops; wall marks: `tools/wall_check.py <photo>`), fine skin texture (the finest band of `band_energy` in `templates/portrait-qa/recipe/measure.py`, on the upper face, healed spots excluded) is at least 80 % of the base's for each photo, and the number is in `proceso-notas/`.
   Then run `recipe/grade.py <photo>`: it writes the master `editadas/<photo>.tif` and the camera original `editadas/<photo>-antes.png` that steps 4 and 5 measure.
4. **References: find, then measure.**
   - The photographer's references come first, whatever they are (a brand or page they name counts: import its photos, from its press kit when it has one); when they gave fewer than three, find published photos of the same kind and subject (a team page, a press portrait, a pet on a beach, a product) by photographers or brands known for photo craft: press kits, newsrooms, photographers' portfolios and editorial sites, at the highest resolution offered.
   - Import each with `tools/ref_import.py` straight from its URL, file or zip (usage: the tool's docstring); it converts in memory, so a JPEG reference never lands in a no-JPEG project. Record its URL, credit and the hand-marked faces, walls and blacks in `recipe/references.py`.
   - Measure each next to the photos and the camera original with `tools/ref_measure.py <ref> <photo> <photo>-antes` ([references/measurement.md](references/measurement.md)): the camera original is the reference for everything a style does not change.

   Done when `recipe/references.py` cites at least three references, all of them this project's and none left from the template (all the photographer gave, then found ones), the README's brief lists them and, when any were found, the photographer's pick, and every row of measurement.md > Tolerances that `ref_measure.py` measures has its number on the sheet or in `proceso-notas/estilos/medida-<ref>.json` for each reference and each photo.
5. **Iterate** until the photo is excellent, on crops or at preview size, one case per affected photo (a fix that helps one site can hurt another). Each round: change one thing, measure with the same code as the references (`tools/style_pilot.py` for panel settings, `tools/ref_measure.py` on a rendered style; usage: their docstrings), write a numbered candidate `proceso/<group>-r<NN>.png` with the reference above it, and compare against the tolerances in [references/measurement.md](references/measurement.md) > Tolerances. A change that touches the wall through the matte follows [references/compositing.md](references/compositing.md). When two rounds in a row move no number toward its target, change the approach instead of the amount.
   Done when every number is inside its tolerance, every case passes the gates in [references/qa.md](references/qa.md), and at 100 % the photo reads **hand-edited** next to the camera original. A number that no change of approach brings inside goes to the README's pending list with the reason it stays, counts as a failed gate in step 8's percent, and is named in the reply. With more than one passing candidate, put them side by side in one sheet in `proceso/` and wait for the photographer's pick before step 6; with one, go on.
6. **Render** only the photo × style that changed (`recipe/grade.py`, and `recipe/styles.py <photo>` for the styles), and scope the QA sheets the same way; run the full set once, at the end of the request. Before the render, keep the previous masters as APFS clones (`cp -c`) in `respaldos/<version>-antes-<change>/` at the project root, with the `editadas/` tree intact (`<version>` the masters' next, `v<N>` after the last in the README's change log; `<change>` a short name, as in `respaldos/v8-antes-ojeras/`; one folder per version, since the tools take one); they are the regression baseline, not something the photographer looks at. Then write what is expected to change, photo × style and where, to `proceso-notas/<version>/esperado.txt`; step 7 checks against it. When a fix in shared code would move approved masters nobody asked about, render the one asked about first, show it, and ask before the rest. Command, speed and who runs it: [references/speed.md](references/speed.md); master format: [references/delivery.md](references/delivery.md) > Masters.
   Done when the clones and `esperado.txt` predate the render, the masters are written and every skipped output had an unchanged input fingerprint.
7. **Regression and QA.** Compare decoded pixels against those clones with `tools/compare_masters.py` (file hashes differ anyway: the ICC header carries a timestamp). Then check at 100 % (200 % on contours) at fixed zones: face, hair edge top and sides, clothing edge, far wall, black clothing. Re-run the gates in [references/qa.md](references/qa.md) on every changed photo × style at native resolution: step 5 passed them on crops, where edge defects don't show. For a deliverable, one auditor subagent ([references/speed.md](references/speed.md)) then checks the changed masters at the same zones and returns a defect list.
   Done when every master is pixel-identical, changed exactly where `esperado.txt` names, or listed `NUEVO` by `compare_masters.py` and named in `esperado.txt`; the qa.md gates pass on every changed master at native resolution, and each remaining defect, the auditor's included, is listed in the README's pending list.
8. **Hand over.** Write before/after sheets with `tools/antes_despues.py --before respaldos/<version>-antes-<change>/editadas <photo>:<style> ...` for each photo × style that changed (copy it from `templates/portrait-qa/tools/` into `tools/`; it imports no `recipe/` module and runs under `.sin-jpg`; usage: the tool's docstring): camera | before | after | what changed, as a dE76 map, written to `proceso/`. A master with no pixel over dE 1.5 gets no sheet, only a line saying so; one with no before (a style rendered for the first time) gets a `nuevo` line. Reply as "What the photographer reads" says, with an honest percent done: the share of gates passed, with what is left in the README's pending list.
   Done when the README has the deliveries line (dated, as in the export branch), today's dated change-log entry and every failed gate in its pending list; each changed photo × style has its `proceso/antes-despues-<photo>-<style>.png` or the tool's `sin cambios` or `nuevo` line; and `pgrep -fl` shows nothing the agent started still running.
