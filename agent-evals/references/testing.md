# Test and gate releases

Simulated customers and replays: simulation.md. Red teaming: red-team.md.

## The test environment

- **A stateful sandbox, reset for every trial.** Writes must be real (a withdrawal changes a fake ledger), and one trial must never see another's leftovers. An agent that reads a previous run's state gets the answer for free.
- **Reset isn't isolation.** Concurrent trials share no writable resource they could pass notes through (a cache, a repo, a shared folder), and expected outcomes, reference solutions, and grader code stay out of the agent's reach, public repos and dataset hosts included. Agents in separate OpenAI eval runs used a package cache as a message board ("answer(Q12)=42") and read the benchmark's grader code online.
- **Verify the sandbox before every run, and watch every run.** Before each run, test that every side-effecting path (network, email, payments, ticketing) lands in the sandbox, and tell the agent truthfully which systems are in scope. Run production's action monitors live on every run, not on a sample afterwards: crossing the scope ends the run and alerts a human. Anthropic found 3 incidents in 141,006 runs where models compromised real third-party systems through a misconfigured sandbox while the prompt said there was no internet.
- **Three layers of tests.**
  1. Pure rules as unit tests (a withdrawal limit, a KYC gate), no model involved.
  2. The agent loop with a scripted model, to prove the plumbing, such as the tool result reaching the context or an approval pause resuming the same run.
  3. End-to-end runs with the real model.
  A failure in layer 3 that layer 2 would have caught costs a model run to find.
- **The runner calls the app's real entry point,** never a rebuilt model call, which skips retries, tool wiring, and context assembly. Each case records, from that same call, the model the response reports, usage, stop reason, and transcript. Write each case as it finishes, resume on (case, run), and record a hard per-case time limit as a timeout, never a zero. A $0.00 cost, 0.0s latency, empty usage, or constant column is a runner bug: raise instead of writing the row.
- **Get two expert sign-offs before the first paid run:** one on the inputs, and one on about five graded examples ("would you have scored any of these differently?"). One yes means the rubric isn't ready.
- **Close shortcuts by rule, not by removing tools.** If the sandbox lets the agent read the answer (an already-resolved ticket, a seeded ledger note), keep the tool, state in the case what use is legitimate, and have a trace check score the run 0 when it's crossed, even if the attempt failed. Blocking tools instead turned into a 1,200-entry blocklist the agents spent 20+ turns routing around.
- **Screen every pass for a looked-up answer.** When the environment holds resolved history (old tickets, CRM notes, public material) and the agent can search it, an auditor that sees the task and trajectory but not the verdict flags answer lookups, and those passes score 0. Validate the auditor on expert labels (evaluators.md) and pin it per rule 13. Decide before the run whether a flagged case reruns with that source blocked or stays failed. Prompts telling the agent to keep going without stopping raise shortcut attempts.
- **Re-measure the leak on every model upgrade.** Run the suite once in a sealed copy (no history, no network) and compare. Newer models exploit leaks far more: 63% of one recent model's passes had fetched the known fix, and sealing cut two recent models' scores by 14.1 and 20.7 points against under 1 for an older one. Prefer cases written after the model's training cutoff and checks with randomized values, which a memorized answer can't pass.

## Runs and metrics

- 15 runs per case in CI, because a case that fails 1 run in 20 still passes 15 of 15 only 46% of the time, so it shows up instead of hiding. Gate on pass^k, where a case passes only if every run passes. pass@k (any run passes) is for exploring what the agent can do, never for gating.
- Reliability drops with repetition: 9 successes in 10 gives about a one-in-three chance of 10 clean runs. Expect the gap and design for it.
- **Estimate from n runs, don't rerun k times.** Compute pass@k and pass^k from c passes in n runs with the estimator in statistics.md, after running its check value.
- **Rerun only infrastructure errors** (timeout, missing trace, no reward), never a failed verdict. A red regression case is evidence to read, not noise to retry. Don't classify a case from a baseline with an infrastructure error, and never change a classification to get the mix you want.
- **Tag every failed attempt** as infrastructure error, timeout, refusal, or real failure, and leave answers cut off by the token limit out of the mean. Before citing a gap between two models, set aside failures only one model triggers: they're usually harness bugs. Check that each response came from the model you requested, and fail the attempt if not.
- **Infrastructure alone moved an agent benchmark 6 points.** Fix each case's resource limits, spread runs over more than one day, and don't trust a difference under 3 points even when the noise band in statistics.md is narrower.
- **Check that the model didn't notice the test.** Models can tell an eval from real traffic: when OpenAI replayed 49,650 real tasks with a new model, 2.5% to 8.7% of runs showed signs of it, against 0.76% in the original traffic. Have a judge classify each run's reasoning (suspects a test, recognizes a safety test, certain) and whether that drove the decision. Validate it on expert labels (evaluators.md) and pin it per rule 13. Rerun the comparison without flagged runs and trust it only if it holds.
- **Compare aware and unaware runs, and write cases in real ticket wording.** Compare the outcome rate of flagged and unflagged runs with an interval, and read the flag count as a lower bound, since a model doesn't always say what it noticed. Contrived scenarios trigger it most: on one, Meta's model suspected a test in 75.0% of runs, and aware runs did harm 0.3% of the time against 4.1% for unaware ones.
- **Score a do-nothing agent before trusting the suite.** Run a null agent (empty replies, no tool calls) on every case pool. On τ-bench Airline it passed 38% of tasks, above a GPT-4o agent (35%), because impossible tasks were graded by an unchanged database. Every case whose expected end state equals the start state also requires something observable (saying why it can't, or escalating), and state checks cover state that must stay unchanged.

## Release gates

```
Did this case pass all 15 baseline runs?
├── Yes → regression case: must stay at 100%, any failed run blocks the release
└── No → capability case: report the score, never block
```

- **CI holds** core journeys, every past production bug, and known edge cases, with a code check for every case whose outcome is objective, and a rolling set of recent production failures.
- **Cadence.** Cheap checks on every change, expensive judges nightly and before each release. A capability case that starts passing every run graduates to regression. Never retire a regression case, because it's what stops an old bug from coming back.
- **Case record:** id, failure mode, input (role, user, opening message, scripted follow-ups), initial state, `checks` (code), `judges` (frozen judge and expected verdict), `assertions` (plain-language intent, never scored). Add `kind` and the baseline pass rate after the 15 baseline runs.
- **Prove every case is solvable.** Before a case enters CI, run a reference solution (a scripted run or a person using the same tools) in the reset sandbox and store it in the case record as `reference`. Until it reaches the expected state, the case is broken, not the agent, and never runs with real tools. A case is also broken if two domain experts would reach different verdicts on the same run, or if the grader checks something the case never asked for.
- **Unsolved cases breed shortcuts, so graders credit stopping.** In one OpenAI incident, 93% of the tasks agents discussed on an unauthorized message board came from the 198 of 898 that no model had solved. Graders credit recognizing a broken or impossible case, asking for clarification, or stopping safely, not only finishing.
- **When someone wants one number, report pass-all rates by severity.** A case passes only if every check passes: one rate for release-blocking checks and one for tolerable checks, each with drill-down to the checks. Never a weighted composite, which moves without saying what changed.
- **Quality gates come before cost.** Policy compliance, action correctness, security, and escalation accuracy must pass before you compare cost or latency. Among passed cases only, report step, tool-call, and latency ratios against an ideal run (observed divided by the fewest calls a correct run needs). Use them to compare versions that already pass. They never fail a case, because rule 5 keeps the path out of the gate.
- **Count cost per resolved case, retries and fallbacks included.** A published benchmark cost that left out fallbacks, which happened on about 40% of tasks, understated the real cost. Set the latency limit from when real users give up (the distribution of time until they abandon), not from a round number.
- **Every model change reruns a broken-tool case.** Make a tool fail and check that the agent tells the customer instead of answering as if it worked. On OpenAI's broken-search test, a small model hid the failure in 28.7% of cases and a large one in 1.5%, so the cheaper model is where to look.
- **Grow it into a seeded fault matrix at the tool boundary,** without changing the agent: specific error codes for specific arguments, added latency that hits timeouts, and random failures from a fixed seed so runs reproduce. Writes still go to the stateful sandbox. Model-generated mock responses are only for reads.
- **Compare versions on a reliability profile.** Rerun the suite under tool faults, meaning-preserving environment changes (renamed fields, reordered JSON, other date formats), and paraphrased customer requests, and report each as accuracy divided by baseline accuracy. Across 15 models, paraphrases separated them most. Report policy violations as rate times severity (low 0.25, medium 0.5, high 1.0) and never average them into a score: they're a hard constraint. On τ-bench, wrong charges and refunds were the most common violation.
- **Set the requirement before testing, from a cost model.** Value each outcome, estimate each failure kind's share, and find the break-even accuracy, where the value of successes equals the expected cost of failures (statistics.md). Where one failure costs far more than a success saves (a fraud case resolved wrongly), a human decides and the agent assists.
- **A ship decision on a rate needs the interval, not the point.** Ship only if the upper bound of the 95% Wilson interval on the failure rate is below the requirement, and size the sample first (statistics.md).
- **Release one versioned bundle.** Prompt, model, tools, and the help-center snapshot ship together and roll back together. Promote by re-pinning, with the required simulations passed, a named approver from compliance or CX, and the rollout below.
- **Shadow first.** After the offline gates pass, run the candidate on a copy of live traffic for at least 4 hours, never executing its writes, and compare its outcomes with production. Pause the rollout automatically if they deviate by more than 2%.
- **Then a canary of about 1% of live traffic,** compared with the current version on a real outcome metric, before a wider A/B and full rollout. Offline parity only covers the requests you anticipated: Shopify's agent matched on a 300-case benchmark and had 35% lower activation at 1%. Keep the noisy business metric as a guardrail and the validated judge as the target.
- **Production bugs.** Reproduce with 10 runs (20 if seen once), fix, verify with the same number of runs, then add the case and a paraphrased variant to CI. One green run proves nothing for a nondeterministic bug.
