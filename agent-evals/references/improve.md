# Improve the agent against the eval

## Before the first change

**Check the eval before climbing it.** A stronger model must score higher, and the best model at its highest effort must stay well below 100% for reasons other than broken cases. If scores don't rise with capability, ambiguous cases or a miscalibrated grader are capping them. If the current version already scores about 95% or more, there's no quality left to measure: aim at cost or latency with quality held.

- **Pick one target.** The failure mode with the highest prevalence times severity in the last error analysis that the prompt, a tool, or the harness can change, and that at least one development case scores. Write it down with three trace ids that show it. A fix aimed at no named mode can't be judged a fix. Check where it concentrates (a version, a scenario) before choosing the change.
- **Lock every model first, with everything that serves it.** Run each model you will compare on one case, replace any that can't finish it, then freeze model, effort, provider or gateway, and harness. Each model runs with the settings it will ship with (context handling, reasoning kept across turns, prompt, safeguards), or you declare one standard harness before seeing results: one model scored 13.3% on a stripped harness and 38.3% with reasoning kept and compaction. Swapping anything after the split makes the comparison meaningless.
- **Check what the provider actually served.** Record each run's reasoning and output tokens, and before trusting a new provider or gateway, reproduce a score the model developer published. The same effort label maps to different budgets across gateways, and degraded serving (quantization, chat templates, context length) happens even at commercial providers.
- **Never pick a model on public benchmarks built from public data.** Every frontier model tested reproduced SWE-bench Verified gold patches or task details. Keep your cases out of public repos, marked with a canary string, and before trusting a score on a public or reused set, check whether the model reproduces case-specific details without solving the task.
- **Split once, then freeze it.** Group cases by kind (regression or capability) and by whether they change data, and put about one third of each group in the test set. A group of one stays in development; a larger group keeps at least one case on each side. Balanced groups make both sides score the same behaviors.
- **Assign within groups at random, never by baseline score,** which builds regression to the mean into the result. Store case ids and a hash, and never recreate the split.
- **Set a search budget in evaluated case runs** (150 in Hamel Husain and Shreya Shankar's course homework) and charge it before each run. During search, a case that changes data runs 5 times and a read-only case once, to stretch the budget; that's a search economy, not a gate. The test batch and CI run every case 15 times, because there each case decides something. Refuse a run that would exceed the budget, and return the unused runs when one crashes.
- **Record the baseline** on development: commit, prompt hash, model, score, and the share of data-changing cases that pass all 5 runs. If time has passed or the environment changed (dependencies, model snapshot, data), run an unchanged control and compare against it, not the old baseline.
- **Measure build variance when the change builds something the agent reads** (a retrieval index, help-center chunks, a memory store, summaries). Rebuild it 2 or 3 times with no change and score each build: that spread is the floor a one-edit effect must clear. Three builds of one prompt spanned about 7 points against rescoring noise near ±1.4. If the spread exceeds a plausible effect, build K times per variant, compare pooled means, and rebuild the control too.
- **Register before round 1:** the quality floor with its rationale (never the baseline mean read afterwards), the gates for keeping a change (development quality at or above the floor, cost within a set margin, the predicted mechanism visible), and each candidate's point prediction with an 80% interval on score and cost, plus a falsifier. Put cost in the objective: a quality-only climb raised cost per deliverable 75%.

## The loop

1. **Don't choose the layer by reasoning about the failure. Probe each layer once by hand** before automating: one prompt change, one tool change (its description or its code), one harness change (retrieval, step control, context, result checks). Write the predicted effect before editing, including the mechanism you expect to see (more escalations, a tool called earlier). The layer that moves the target is where to search.
2. **One change per attempt, in one layer.** Commit it, run development, and keep it only if the score rises, the data-changing pass share doesn't drop, and the registered gates pass. Otherwise revert to the last kept commit. A mean that rises while writes get less reliable is a worse agent.
3. **Before spending a round, compute the most the fix can gain:** the cases showing the behavior times what they lose. If that's inside the noise floor, it's a stall: sort the failures or add cases and runs, never inflate the change.
4. **Log every attempt, reverts included:** candidate, layer, files, rationale, predicted effect, how often the predicted mechanism fired, score, write pass share, decision, commit, result file. A search whose failures aren't recorded can't be audited or resumed.
5. **Stop after 2 changes in a row that don't improve,** or when the budget runs out. Then stop editing and sort every remaining failure by cause. That finds broken cases and graders.
6. **Two exceptions to one change per attempt.** If the sort shows many independent buckets each costing 2 failures or fewer, none measurable alone, one breadth pass may cover them all. If one bucket hasn't moved after 3 rounds of correct-looking changes, stop and re-read its rubric. A changed rubric is a new judge: validate it, re-grade every stored round, and decide whether earlier rounds stand.
7. **Choose the method by layer.** An automated prompt optimizer (GEPA) when the fix is prompt wording; a coding agent making one allowed change at a time when it may be a tool or the harness. Never use or report an optimizer's search score: rerun its best candidate with the normal development eval and use that number. The search kept its luckiest run, so its score is biased upward.

## Search discipline

- **Never, during search:** run or read the test set, edit cases, judges, graders, tests, or the budget, raise a timeout, change a seed or sample size, or weaken an authorization check. Each one raises the score without improving the agent. If runs time out, the timeouts are failures to read and fix, not a setting to loosen.
- **When an agent runs the search, enforce that wall in the environment, not the prompt.** Keep test cases, expected outcomes, and grader code outside its filesystem and network reach, log every access attempt, and discard any run that made one: 17% to 42% of developer-agent runs probed for held-out data or the grader. A separate monitor reads each proposed change before it runs and scans transcripts for cheating, which one found in 39 of about 1,600 (fetching test labels, cherry-picking runs).
- **Isolate the analyzer.** The outer session sees scores only. Each round, a fresh analyzer gets an explicit list of development trace paths, describes the failing behavior instead of pasting case content, and never adds a capability that helps eval cases but is rare in production (an OCR tool the eval rewards and users never need).
- **Check first that the eval's noise is smaller than the smallest gain you'd act on** (noise band and smallest detectable difference in statistics.md), or add cases. A gain that doesn't show the mechanism you predicted is rejected, whatever the score. Prompts, skills, and tool descriptions are cheap to change and revert. Harness code isn't. Never paste failing transcripts into the prompt.
- **Rerun any would-be incumbent whose margin over the floor sits inside the noise.** One winner passed 11 of 20, then 6 of 20 on the identical config. A false keep is the expensive error, because it prunes the true winner.
- **Read passing runs too.** When a case or grader is new, and after each improvement round, read a sample of passes with the grader's reasoning. Look for shortcuts: extra articles cited to satisfy a citation check, an action claimed that the trace doesn't show, the answer read from the environment, a proxy met without finishing the task. A pass earned by a shortcut is a grader bug.

## Freeze, then test once

- **Pick the final candidate by the target first,** then development score, then the write pass share. A candidate that fixes the target and makes writes more reliable is worth a small drop in mean score.
- **Confirm before freezing.** Rerun the chosen candidate 3 or more times on development and report that confirm, never the selection run: a selection run read cost -50% where fresh runs read -46%, and re-grading shrank a +9-point win to +3.
- **Freeze it before any test run:** commit, prompt hash, model, development scores, and a hash of the cases and judges, verified unchanged since the split.
- **Run the test set once, as one planned batch of every configuration you compare.** Never change the agent after reading test results. Those cases are now development knowledge, and a later change needs a new test set.
- **Compare configurations so each difference has one cause.** The batch runs the starting version on each candidate model and the final version on the development model, never a comparison on development cases, which already shaped the final version. Starting versions across models show the model's effect; starting and final on the same model show your change's effect.
- **Add the final version on every other model it will serve.** Prompt gains of +30 and +15 points were each specific to one model.
- **Search model and effort as one grid,** because the cheapest acceptable configuration is often a stronger model at lower effort. Enter at the top tier's lowest effort, step down a tier on a pass and up in effort on a fail: about tiers + levels cells, not tiers × levels. On a 44-ticket support benchmark this moved from 4.6 to about 1 cent per ticket while held-out accuracy rose from 78.6% to 90.5%.
- **Never assume more effort scores higher, and judge an effort cut by aggregate non-inferiority over several runs,** never case by case. Higher effort scored the same or lower in 21 of 36 model, scaffold, and benchmark combinations, and at lower effort failures move between cases.
- **Report the frontier.** A configuration is dominated when another scores the same or higher at the same or lower cost, with at least one strictly better. The rest form the frontier, the tradeoffs worth choosing among. Price every model from one date, and count the agent's calls only, never the judges'.
- **Name the claim and the budget in every report.** Say whether it shows best achievable capability, a controlled comparison, or safeguard robustness, and report turns, tokens, attempts, wall-clock, and cost per successful solve. A score still rising at the largest budget you tried is a lower bound under that budget: one rose up to 59% from 10M to 100M tokens and was still climbing.
- **Confirm the gain on real-traffic cases** and report them apart from synthetic ones. Gains shrink on production-like cases, partly because models behave better when they can tell they're tested: training cut covert actions about 30 times on synthetic tests but deception on a production-like set only from 31.4% to 14.2%.
- **Report the final version against the baseline on the test set** as the per-case difference with the exact paired test and its wins, losses, and ties (statistics.md), never two separate intervals that overlap, and don't merge a gain that sits within the noise.
