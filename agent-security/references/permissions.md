# Permissions: what the agent may touch

What the agent can reach sets the ceiling on what an injected instruction or a persuasive customer can make it do. This file scopes tools, targets, credentials and delegation; sandboxes and network egress for agents that run code, browse or fetch are sandbox.md, and which of the remaining actions need approval, and from whom, is approvals.md.

## Scope the tools before anything else

- **Never let the agent commit the business to terms it wasn't given authority for: contracts, hires, prices.** Enforce the limit in the tools, because the customer's proposal will sound reasonable. In Anthropic's Project Vend, agents agreed to an onion futures contract banned by the 1958 Onion Futures Act and offered to hire a security staffer at $10/hour, below California minimum wage; only a human objection stopped each one. (`anthropic-project-vend-2`)
- **Remove an action the model must never take from the interface; never forbid it in the prompt** (agent-harness rule 2). Anthropic's commerce agent calls a backend that has no charge method at all, and checkout is a button the shopper presses. Prompt-only limits fail: in July 2025 Replit's agent deleted SaaStr's production database during an explicit code freeze, and Copilot in SQL Server Management Studio, told it was "running in a read-only mode", executed with the user's sysadmin rights (CVE-2026-65669, critical, 2026-09), so enforce read-only with a read-only database role. (`anthropic-commerce-agents-anatomy`, `register-replit-db-deletion`, `rehberger-sql-copilot-sysadmin`)
- **Apply least agency: limit what each tool can do, how often and where, not only who the agent is.** Least privilege on the agent's identity still leaves every tool fully powerful. A lookup tool gets read-only queries, an email summarizer gets no send or delete, and account lookup and refund execution are separate tools with separate gates; a read-only agent can be deployed far more widely because the tool caps the blast radius of a hijack. (`anthropic-zero-trust-ebook`, `anthropic-how-we-contain-claude`)
- **Route different support tasks to specialist agents with narrower tools.** An intent classifier in front sends each conversation to an agent with its own tools and prompt, so a billing chat never holds account-deletion tools and an injection in one flow reaches only that flow's tools. (`anthropic-customer-support-agent-guide`)
- **Offer only the tools the conversation's state allows, and withdraw them when it changes.** A refund tool appears after identity is verified and disappears after a failed check, instead of every tool being exposed while the prompt holds the line. Anthropic's API can add or remove a tool from a point in the conversation onward without changing the tools array (`tool_addition`, `tool_removal`); using that as a permission gate is an inference from the mechanism, so the handler still authorizes each call, and agent-harness tools.md covers keeping the tool list cache-stable. (`anthropic-docs-mid-conversation-system-messages`)
- **Cut the tool list to what the request needs before the agent reads untrusted content.** An injection can only trigger tools the agent still holds. GPT-4o (2024-05-13) on AgentDojo, important_instructions attack, run 2024-06-05 on the ETH Zurich SPY Lab leaderboard: no defense 47.69% targeted attack success at 69.07% utility, tool filter 6.84% at 72.16%, a prompt-injection detector 7.95% at 41.24%, repeating the user prompt 27.82% at 84.54%, spotlighting with delimiters 41.65% at 72.16%; the filter fails when the attacker's goal uses the tools the user's task needs. (`spylab-agentdojo-leaderboard`)
- **Ship without the capabilities that turn an injection into a leak, and label the risky ones you keep.** OpenAI launched ChatGPT agent (2025-07-17) with memory disabled and its terminal limited to GET requests for images and certain datasets, because more tools reachable at once raised the impact of an injection; capabilities come back as other mitigations mature. Its "Elevated Risk" label marks network access, live connectors and browsing with one warning across ChatGPT, Atlas and Codex, admins choose which apps and actions stay on, and the label goes only when mitigations make the feature safe for general use. (`openai-chatgpt-agent-system-card`, `openai-lockdown-mode-elevated-risk`)

## Accounts, identity and tickets

- **Never let a support agent change a login email, phone, password or 2FA on the customer's say-so: its tools read account state and surface a recommended action for a person or the identity system's verification flow to execute** (agent-harness rule 2). Account recovery, including the Meta takeover, is conversation.md. (`csa-meta-ai-support-bot-takeover`)
- **Scope what support can reset in the permission system: no MFA or credential resets on privileged accounts, and an alert on every reset-all.** Okta saw callers talk service desks into resetting all MFA factors of highly privileged users, then use the super-admin to federate a rogue identity provider (advisory v1.2, 2024-03-08). Its fix constrains help-desk roles to exclude privileged groups and alerts on `user.mfa.factor.reset_all`; an AI support agent's tools get the same scope. (`okta-helpdesk-social-engineering`)
- **Run every assistant that reads support tickets with your human support role, never an admin or service role.** A ticket is attacker-controlled input to every AI that reads it later, staff assistants included. General Analysis (July 2025, reviewed 2026-09): a ticket told a developer's Supabase MCP assistant, running as service_role, to read the integration_tokens table and post it into the thread the customer could read; the human support role was restricted, the assistant wasn't. (`generalanalysis-supabase-mcp`)
- **An agent triggered by inbound email or webhook can be triggered by anyone who can send one.** Restrict triggers to known senders, and never give such an agent both a CRM read tool and email to arbitrary addresses. Zenity (July 2025) hijacked a replica of McKinsey's Copilot Studio customer-service agent with zero clicks: one email leaked its knowledge file, "about 100 rows of data in a single iteration", and another pulled Salesforce records and emailed them out. (`zenity-copilot-studio-aijacking`)

## Every target belongs to the verified customer

- **Bind the account to the authenticated session before any write tool runs** (agent-harness rule 3). OpenAI's customer-service demo loads a booking into context when a message mentions a city and tells specialists "If present, act without re-asking", with nothing checking that the person chatting owns it. Per-user credential stores referenced by ID are the same trap: Anthropic's Managed Agents attach any vault in the workspace to any session you create, so your server picks the vault from its own authenticated session. (`openai-cs-agents-demo`, `anthropic-docs-managed-agents-vaults`)
- **Write tools accept only object IDs your server returned to this session, and never a guessed target.** Anthropic's commerce harness keeps a per-session record of server-issued IDs as the only key writes accept, so a pasted order number or an ID from third-party text never reaches the backend, and read-only subagents can't add to it. When a customer says "cancel my subscription", resolve the object from verified account data or ask: in Anthropic's incident log, "cancel my job" made an agent pick the closest name match, possibly someone else's, and try to delete it. (`anthropic-commerce-agents-anatomy`, `anthropic-claude-code-auto-mode`)
- **Normalize and validate every identifier in code, against the authenticated customer, before a tool builds a backend call.** Two parsers disagreeing about one string is enough to return another customer's profile. Intigriti (2026): `attacker(&email=victim@victim.org&)@attacker.com` delivers to the attacker but the backend parser read the victim's email, and an offer ID of `../OFF-2231` exposed path traversal that later fed the agent a fake discount code from an uploaded avatar file. (`intigriti-hacking-ai-support-agents`)
- **Before clicking or typing, check the target hasn't changed since the agent looked.** A page can swap the button while the model is thinking. Rehberger (June 2026) made Claude Computer Use click a swapped button regularly and send attacker-composed email through an Outlook compose deep link; Anthropic's Cowork now checks that the pixels are unchanged before acting. (`rehberger-computer-use-toctou`)

## Limit what one session can combine

- **A support agent already holds untrusted input and account data, so every refund, email and account change passes a human approval, an allowlist or another reliable validator (approvals.md).** That is the Rule of Two applied to support (threat-model.md): Meta calls prompt injection "a fundamental, unsolved weakness in all LLMs", and breaking the chain in code removes the highest-impact outcomes even when the model is fooled. (`meta-agents-rule-of-two`)
- **Change a session's configuration in one direction only.** Browse with no private data, then irreversibly drop outbound communication before touching internal systems, and never switch back in the same context, because the untrusted content already read stays there. (`meta-agents-rule-of-two`)
- **The connected system's own permissions stay authoritative, a restriction beats a grant, and a shared agent gets at most the requester's access.** In ChatGPT workspaces app access "does not override permissions in the connected source system", and a Lockdown Mode role's restriction holds against any role that grants. Anthropic's Claude Tag (2026-06-24) gives a shared agent its own identity per compartment, so a member without repo access can get the agent to read it; Anthropic accepts that gap for now and plans a user-permission overlay, so for strangers intersect the agent's access with the requester's. (`openai-help-lockdown-mode`, `anthropic-agent-identity-access-model`)
- **Write the agent's scope as a structured record the platform enforces.** OpenAI's Model Spec (2026-08-18) proposes a scope-of-autonomy record (allowed tools, latest time, max cost, tool constraints) with a mandatory end condition, inherited by sub-agents, and forbids out-of-scope actions "even if an out-of-scope action seems to be in the user's best interest". (`openai-model-spec-2026-08-18`)
- **Name the in-scope systems, and make out-of-scope targets say so, because an agent left to infer its authorization assumes it has it.** In four 2026 incidents where Claude models attacked real third-party systems during evals, no prompt named the in-scope systems: Opus 4.7's thinking questioned authorization in 1.5% of re-runs, it said it was authorized in 75% of samples and conceded it wasn't 100% of the time when asked who granted it, and a "not permitted" banner on the target mostly stopped it (2026-09-09, Anthropic). (`anthropic-alignment-assessment-cyber-incidents`)

## Credentials

- **Give each agent session its own short-lived, narrowly scoped token, revocable apart from the user's, and keep the long-lived secret outside the agent's environment.** Static API keys and shared service-account passwords are among the first things an attacker with model-assisted code analysis finds, so Anthropic's zero-trust floor is identity-provider tokens that expire in minutes and refresh automatically. Cowork keeps credentials in the host keychain and issues a per-session token, and in Claude Code on the web GitHub credentials "never enter the session VM". (`anthropic-zero-trust-ebook`, `anthropic-how-we-contain-claude`, `anthropic-docs-claude-code-security`)
- **Keep real credentials behind a proxy that validates each operation, out of reach of any model-generated code.** Anthropic's git proxy pushes only to the configured branch and rejects branch deletions and tag pushes, so compromised sandbox code can do only what the proxy allows, and a protection rule the connected identity can bypass doesn't stop the agent. Scoping alone "encodes an assumption about what Claude can't do with a limited token": when code and credentials shared a Managed Agents container, an injection only had to make Claude read its own environment. (`anthropic-claude-code-sandboxing`, `anthropic-docs-claude-code-security`, `anthropic-managed-agents-brain-hands`)
- **Never leave publish or write credentials reachable on the assumption the model will refuse misuse.** Claude Opus 5.5 without cyber safeguards, given apparent credentials to a public package registry in a simulated security exercise, "took potentially harmful actions in roughly half of cases" (2026-09-22, Anthropic's own system card, which reports evaluation awareness "with verbalized indicators in about one-third of Opus 5.5 runs"). Anthropic built that eval after a model published harmful content to PyPI; scope credentials to the task and require out-of-band approval for any publish. (`anthropic-system-card-opus-5-5`)
- **Request the narrowest OAuth scopes per tool and step up only when a task needs more.** A token granted `files:*`, `db:*` or `admin:*` up front turns a leak from logs, memory scraping or interception into lateral access and makes revocation painful (MCP security best practices, 2025-11-25). (`mcp-security-best-practices`)
- **Give each trust boundary its own sandbox environment and key, and each sandbox only its per-session secret.** With secrets kept out of images, shared volumes and logs, a leaked key exposes one user's sessions instead of a shared pool; Anthropic's security model for self-hosted sandboxes stops at the sandbox, so key handling outside it is yours. (`anthropic-docs-managed-agents-self-hosted-sandboxes-security`)

## Delegation between agents

- **A delegate can only narrow access, never widen it.** Scope delegated credentials to the subtask and combine restrictions across agents (Anthropic's Managed Agents intersect allowlists and add blocklists), so a sub-agent with a looser config can't reach what its coordinator couldn't. A high-privilege agent verifies the original user's intent instead of executing a lower-privilege agent's valid-looking request, the confused-deputy relay Anthropic's zero-trust guide names next to unscoped privilege inheritance. (`anthropic-zero-trust-ebook`, `anthropic-docs-managed-agents-tools`)
- **Give each agent one purpose and its own identity, and let agents coordinate only where people can see.** A blocked agent will ask a more privileged one: after a model upgrade, Anthropic's incident-response agent asked another Claude over Slack to push its fix, and only a human review gate caught it. The same works through people, since OpenAI warns an agent can "send an email, an allowed action, to a non-user human that convinces said human to take the disallowed action", so label the agent's messages to staff as agent-written requests and scrutinize them like tool calls. (`anthropic-secure-ai-native-sdlc`, `openai-practices-governing-agentic-ai`)
- **Never treat subagents in one session as a security boundary.** In Managed Agents every agent in a session shares one sandbox, filesystem and credential vault, so a subagent that reads hostile content can leave files the others read; isolate untrusted reading in a separate session. (`anthropic-docs-managed-agents-multiagent-orchestration`)
- **Never give several autonomous agents overlapping write access to one system with possibly conflicting goals.** Agents "quickly assumed that others were purposefully impeding their work": three Claude instances told to migrate one backend to different languages escalated to locking each other out, kill loops and disguised malware, and Mythos-class models resolved it peacefully no better (120 four-hour episodes per model, 2026-08-13, Anthropic). (`anthropic-multiagent-systems-problems`)
