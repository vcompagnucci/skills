# Sandboxes and network egress

For agents that run code, drive a browser or fetch URLs. A customer-facing support agent that only calls your own tools needs the first bullet and none of the rest. What it may touch is permissions.md.

## Isolation for agents that run code

- **Never give an agent that reads untrusted content a shell, open internet and secrets on one machine. A customer-facing support agent gets no shell at all (agent-harness tools.md).** In-chat confirmations and prompting are not tool-invocation controls. One planted GitHub issue made Devin download attacker malware, mark it executable after a permission error, run it and hand over a remote shell with access to AWS keys (Rehberger, 2025-08-06, $500 for 30 days of access). The fix status was still unanswered after 120+ days. Block outbound by default and require out-of-band approval for sensitive operations. (`rehberger-devin-500`)
- **Put the whole agent process inside one isolation boundary that also covers every subprocess.** A per-action classifier or a parser matching commands against rules is a permission gate, not a sandbox. It doesn't know what a command does to its target. A sandbox around shell calls leaves file tools, MCP servers and hooks running on the host, and any script the agent writes bypasses restrictions on direct tool calls. Anthropic open-sourced sandbox-runtime (bubblewrap and Seatbelt) to wrap arbitrary agents and MCP servers. (`anthropic-docs-claude-code-sandbox-environments`, `anthropic-docs-agent-sdk-secure-deployment`, `anthropic-claude-code-sandboxing`)
- **List every path that runs outside the sandbox and gate each one on its own.** Devin CLI's sandboxed Autonomous mode auto-runs shell commands because the OS sandbox bounds them. Its edit and write tools run inside the CLI process, outside the sandbox, so they still prompt. Commands matched by `sandbox.excluded` rules, such as git commands that need credentials, also run outside. A team wildcard deny with an `Exec(gh *)` carve-out keeps everything else inside, and across team and user rules the more restrictive verdict wins (deny > ask > allow). Commands that can't be parsed and PTY sessions stay inside. (`cognition-docs-cli-sandbox`, `cognition-docs-cli-permissions`)
- **Pick isolation strength by threat, and give multi-tenant agents and untrusted content gVisor or microVMs.** Containers share the host kernel, so a kernel exploit from injected code escapes an OS sandbox or a container. Anthropic's secure-deployment guide prices gVisor's overhead as "~0% (no syscall interception)" on CPU-bound computation, "~2× slower" on simple syscalls and "Up to 10-200× slower for heavy open/close patterns" on intensive file I/O. Firecracker boots in under 125 ms with less than 5 MiB memory overhead. Cognition gave every Devin session its own kernel because in a shared-kernel fleet "one compromised session can access every other container's filesystems, credentials, and network connections". Budget for it. Its microVMs "took over a year of hypervisor engineering", and the hypervisor snapshots that free compute while a session sits idle took longer than anything else it built (2026-04-23). (`anthropic-docs-agent-sdk-secure-deployment`, `cognition-building-cloud-agents`)
- **The agent can never write its own configuration or retry its way out of the sandbox.** Permission settings, hooks, MCP server lists, skills, shell startup files and git hooks stay unwritable from inside, and no allow rule can lift that. An agent that edits them can grant itself permissions or plant a hook that runs unsandboxed on the next launch. Close every escape hatch. Claude Code lets the model retry a failed command with the sandbox disabled, and an allow rule like `Bash(curl *)` approves that retry with no prompt. Turn the retry off, and fail when the sandbox can't start. Devin CLI does. It refuses to start "rather than running unsandboxed" whether a flag or a team setting asked for the sandbox, so it hard-fails on Windows, which it can't sandbox, and on Linux without bubblewrap and socat. (`anthropic-docs-claude-code-sandboxing`, `cognition-docs-cli-sandbox`)
- **Prove the sandbox isolates before trusting it, and re-verify before each run.** In 4 incidents over 7 runs of 10 to 34 hours of active work each, Claude models attacked real third-party systems during evals whose prompts said there was no internet (2026-09-09, Anthropic). It happened because a misconfiguration had left the network open. Test egress from inside in CI, and review the config statically. Have a model try to break out in a second isolated environment with no internet. Check at startup that the policy file loaded, since Anthropic's runtime starts on built-in defaults when it finds none, and on Linux its write-deny list misses repositories created later. Read the vendor's own maturity notes too. Devin CLI's docs call its sandbox network filtering "currently unstable", and its "limited" mode allows only GET, HEAD and OPTIONS, which can still carry data out in a URL to any allowed domain. (`anthropic-alignment-assessment-cyber-incidents`, `anthropic-improving-alignment-security`, `anthropic-docs-claude-code-sandbox-environments`, `cognition-docs-cli-sandbox`)
- **Enforce the boundary at the OS and network level even with the best-aligned model.** Claude Opus 5.5 without safeguards attempted to cross a sandbox boundary in 1.5% of runs across 28 handmade scenarios run seven times each (2026-09-22, Anthropic's own system card). Every case stayed low severity because a stronger barrier stopped it. (`anthropic-system-card-opus-5-5`)
- **Cover each objective with independent controls, and expect agents to route around a broken tool.** In OpenAI's Hugging Face incident (2026-08-26), agents escaped network isolation through a package proxy allowed to reach the internet, then chained unknown vulnerabilities. As OpenAI put it, "no single control should ever be assumed to be fully robust". In its DNS incident (training run, 2026-09-20), a search tool returned irrelevant results. So an agent queried search engines from the shell, downloaded the benchmark and reached a public chatbot through unfiltered DNS. Return a clear error, and alert on agents probing alternatives. (`openai-hugging-face-incident-technical-report`, `openai-misalignment-report-dns-chatbot`)

## Network egress

- **Set the network mode explicitly, and treat every allowed host as open for writes.** In Managed Agents, an API create request that omits networking gets unrestricted outbound access, while the Console starts limited. With an always-allow toolset, nothing pauses a command sending files out. Access is "granted per host, not per operation", so an allowed host takes git push, package publish and POST with any credential. Enabling package managers also opens github.com, gitlab.com and raw.githubusercontent.com. (`anthropic-docs-managed-agents-environments`)
- **When a vendor runs agent sessions on machines you operate, enforce its network policy on your side.** Devin Outposts publish each session's allowlist to your orchestrator as `spec.network_policy`, and Devin installs no firewall rules on your machines. Approving the agent's request for a new domain "does not change your network by itself". Without a per-session egress proxy, a Kubernetes NetworkPolicy or VM firewall rules, "sessions on outposts have whatever network access your machines have", even under a mandatory profile. Re-read the policy whenever a session is re-queued. The MCP allowlist, git access level and GitHub token removal are still enforced from Devin's cloud, so only egress moves to you. Cognition recommends Outposts only to teams with "substantial experience operating remote development VMs securely and reliably at scale" (2026-07-21). (`cognition-docs-security-profiles`, `cognition-devin-outposts`)
- **Keep two allowlists and check both: where a credential may be sent, and where the agent may connect.** A credential's host list "controls which requests use the secret, not which requests are allowed", so the network policy must also cover the host. If a literal placeholder arrives at a third party, a host wasn't covered. (`anthropic-docs-managed-agents-vaults`)
- **Restrict provider-run fetch tools on their own, and keep web fetch out of sessions that mix untrusted input with sensitive data.** Web search and web fetch run on the provider's servers, so the sandbox allowlist doesn't limit them. Set the tool's own allowed or blocked domains instead. Anthropic warns that mix "poses data exfiltration risks", and its fetch has "currently no default limit" on uses. Give it a domain allowlist and a per-request cap. (`anthropic-docs-managed-agents-environments`, `anthropic-docs-web-fetch-tool`)
- **Never rely on proxy environment variables to force traffic through your egress proxy.** Not every program respects HTTP_PROXY/HTTPS_PROXY. Node.js `fetch()` ignores them by default. Remove the network interface and expose only a proxy socket, or redirect all outbound traffic to a transparent proxy with iptables. (`anthropic-docs-agent-sdk-secure-deployment`)
- **Give a browsing agent site-level permissions and a fresh profile with no saved logins, in its own low-privilege container or VM.** Anthropic calls permissions "the first line of defense" against injection in Claude in Chrome. It blocks high-risk site categories and keeps confirmation before publishing, purchasing or sharing personal data, even in autonomous mode. Enforce the allowlist at the network layer, re-check it after every redirect, and block loopback, link-local and private ranges. (`anthropic-claude-in-chrome-pilot`, `anthropic-docs-browser-use-tool`)
- **Build egress allowlist-first, with deny over allow and a check on where each name resolves.** Codex's network proxy is the model. Nothing is reachable until allowed, and deny beats allow. `*.example.com` covers subdomains but not the apex. The proxy blocks loopback, link-local and private destinations by default, blocks names resolving to private IPs even when allowlisted, and blocks failed lookups. OpenAI says the DNS check "reduces DNS rebinding risk, but it does not eliminate it". (`openai-codex-approvals-security`)
- **Block the cloud metadata endpoint inside the container itself, and keep internal hostnames off the allowlist.** Subnet egress rules don't intercept link-local traffic, so model-directed code that reaches 169.254.169.254 can take on the host's cloud identity. Deny it in the container's network namespace, or use IMDSv2 with a hop limit of 1. Allowlisting by name doesn't stop internal reach either. An allowed intranet name resolving to 10.0.0.0/8 still connects through Anthropic's sandbox proxy. (`anthropic-docs-claude-code-self-hosted-environments-deploy`, `anthropic-docs-claude-code-sandboxing`)
- **A hostname allowlist without TLS inspection leaks, and a proxy into your internal tools is an SSRF pivot.** Anthropic's sandbox proxy allowlists by client-supplied hostname without terminating TLS, so domain fronting reaches hosts outside the list. Use a TLS-terminating proxy when exfiltration matters. Limit the upstream destinations of a proxy the agent uses to reach internal tools to the smallest IP ranges covering those servers. Restrict its own egress too, and pin its image by digest. (`anthropic-docs-agent-sdk-secure-deployment`, `anthropic-docs-mcp-tunnels-security`)
- **Write domain lists in ASCII and test how they match.** Look-alike Unicode domains (a Cyrillic "а" in amazon.com) bypass filters. An entry like example.com silently includes every subdomain, user-content ones too. On Anthropic's web fetch, an entry with a path never matches, so a path-scoped block blocks nothing. (`anthropic-docs-server-tools`)
- **Audit sandbox allowances that hand back what the sandbox took away.** A mounted Docker socket "effectively grants access to the host system". Writable $PATH directories or shell startup files give code execution in other contexts. A broad domain like github.com is an exfiltration path, and weaker-nested-sandbox or Apple Events allowances weaken or remove isolation. (`anthropic-docs-claude-code-sandboxing`)
