# Supply chain: MCP servers, skills, plugins and keys

Every MCP server, skill, plugin and SDK your agent loads runs with the agent's identity, and every tool description is an instruction to your model.

## Installing is running someone else's code

- **Treat installing a plugin, skill or MCP server as running someone else's code with your agent's privileges.** Permission rules and the sandbox cover the model's tool calls, "not the code a plugin runs by itself". An install preview "shows that a hook exists but not what it runs", so read hook commands, server definitions and bundled executables yourself. The MCP spec makes consent MUST-level for one-click local server setup. Show the exact command before approval, then run the server sandboxed with minimal file and network access. Grant more only explicitly. (`anthropic-docs-claude-code-plugins-security`, `mcp-spec-security-best-practices`)
- **Install skills only from authors you trust, and read every bundled file, scripts and images included, with a tool that shows invisible characters.** A malicious skill can plant vulnerabilities or tell the agent to exfiltrate. One that fetches external URLs can turn malicious after your audit when that content changes, so reject or re-audit fetching skills. Rehberger (Feb 2026) backdoored a real OpenAI skill with invisible Unicode Tag instructions that Gemini, Claude and Grok follow. Scan for Tag codepoints and zero-width characters, and strip them from untrusted text before the model sees it. (`anthropic-agent-skills-engineering`, `anthropic-docs-agent-skills-overview`, `rehberger-scary-agent-skills`)
- **A marketplace or vendor scan is not your review.** After ClawHub added VirusTotal and ClawScan, five malicious skills still got through between February and May 2026. One padded its README with 22 MB to exceed scanner size limits (Unit 42, 2026-06-23). Bitdefender found "approximately 17%" of the OpenClaw skills it analyzed malicious (Feb 2026), and Koi found 341 malicious skills on ClawHub the same month. Anthropic's own skill scanning skips skills uploaded through the API or Console, skills that predate it, and CMEK, ZDR and HIPAA orgs. A pass with a warning stays usable. (`unit42-openclaw-supply-chain`, `rehberger-scary-agent-skills`, `anthropic-docs-agent-skills-enterprise`)
- **Review every component against fixed criteria, and never let the author review their own.** An author's review can't catch what the author put there on purpose. Anthropic's enterprise checklist rates bundled scripts, instructions to ignore safety or hide actions, MCP references, network calls and hardcoded credentials as high risk. It also checks file-read plus network tools and read-then-send patterns that leak through the agent's own replies. Its directory rules add that descriptions match behavior and that nothing tells the model to call or interfere with other tools (tool shadowing). They also require that no instruction is hidden, encoded or fetched at runtime, and that the component collects only the data its function needs, never memory or chat history. (`anthropic-docs-agent-skills-enterprise`, `anthropic-software-directory-policy`)
- **Block skills and documents from telling the agent to install a prerequisite.** The ClawHavoc campaign (early 2026) used a fake "prerequisite block" so the agent itself decoded and ran AMOS stealer droppers. Auto-updater skills added cron jobs so the C2 survived skill removal. The C2 still received deliveries three months after disclosure. Route every package install through an allowlisted, human-approved path. (`unit42-openclaw-supply-chain`)
- **Watch for components that steer what the agent recommends without touching data or running code.** Unit 42 found a "money-radar" skill that fetched a remote referrals.json, "approximately 60 products across eight categories", before any financial question. It told the agent to always use its affiliate links, which could change after install. Where the agent recommends products, plans or vendors, source the options from your own catalog and log which component introduced each link. (`unit42-openclaw-supply-chain`)
- **Before an agent opens a repository, audit it for every agent tool's config format, not only yours, and turn off imports you don't use.** A file committed for another tool can start an MCP server or run a hook in yours. Devin CLI imports rules, skills and MCP servers from Cursor, Windsurf, Claude Code, GitHub Copilot, OpenCode and Zed files such as `.cursor/mcp.json`, `.mcp.json` and `.claude/settings.json`, and loads Claude Code hooks from `.claude/settings.json`. "If you don't explicitly configure `read_config_from`, all imports are enabled by default", so set every tool you don't use to false. Rules in subdirectories load lazily when the agent touches files there, and the import docs mention no trust prompt. (`cognition-docs-config-import`, `cognition-docs-cli-hooks`)

## Expose only the tools you need

- **Validate every input at your tool server "even if the model provided them"** (agent-harness rule 2). The model is a confused deputy. Whatever an attacker gets into its context arrives at your server as well-formed arguments. OpenAI's guidance for MCP servers and apps also enforces OAuth scopes on every call (401 on expired or malformed tokens) and requires confirmation for irreversible operations. It keeps secrets and tokens out of anything the model or UI component sees. (`openai-apps-sdk-security-privacy`)
- **Drop any tool argument the tool doesn't legitimately need.** MCP Security Bench (BUPT and UC Santa Barbara, ICLR 2026, v2 2026-03-24) ran 2,000 attack instances on real MCP tools. Its most effective attack was a tool declaring an out-of-scope parameter such as a password, which agents filled 76.5% of the time on average. The tool-invocation stage was the least secure (>70% average attack success). The MCIP detector lowered attack success but over-rejected and hurt utility. (`msb-mcp-security-bench`)
- **Enable a third-party server's tools by allowlist, and deny by name whatever must never load.** On Anthropic's MCP connector, every tool is enabled by default, and tools the server adds later turn on automatically. For a misspelled name in the disable list, "a backend warning is logged but no error is returned". A typo leaves the tool on. The OpenAI Agents SDK filters a server's tools per run, requires approval on sensitive ones by name, and passes tokens in an Authorization header, never the URL. (`anthropic-docs-mcp-connector`, `openai-agents-sdk-mcp`)
- **Allowlist MCP servers by exact command and arguments, never by the name a user gives them, and check what an empty list allows.** Windsurf's recommended "Server ID Only" entry matches the key in the user's own config, so it "allows users to install the GitHub MCP server with any valid configuration, as long as the server ID matches". Its exact-match option pins command and arguments with anchored regexes. Devin CLI's team allowlist starts open. "If no servers are added, all servers are allowlisted by default", and with registry enforcement off users "can also connect to other servers, including custom ones". (`windsurf-docs-cascade-mcp`, `cognition-docs-cli-team-settings`)
- **Re-test tool allowlists, denylists and other admin controls after every platform upgrade, because a release can change what they filter.** From Claude Code v2.1.259, the allowlist stopped filtering centrally managed servers. They started loading with no prompt or notice, and only the denylist still subtracts them. A vendor that swaps the agent under you does the same. The Devin Local agent, now the default for new tabs in Devin Desktop, doesn't support Cascade's "Restrict Tool Calls to Workspace" and "Global tool calling disabled" controls, so admins rewrite them as permission policies. Cascade's terminal auto-run setting and allow and deny lists hold only as a fallback until an enterprise CLI permission config exists. (`anthropic-docs-claude-code-managed-mcp`, `cognition-docs-cli-controls`, `windsurf-docs-cascade-mcp`)
- **Connect to the MCP server the service vendor runs, keep per-call approval on until you've reviewed what it requests, and log every payload you send.** OpenAI's example is Stripe's own `mcp.stripe.com`, not a third-party proxy. Third-party servers "may request for data that you may not always be comfortable sharing", may hide injections and "may update tool behavior unexpectedly". Data sent there leaves your ZDR and residency guarantees. (`openai-mcp-connectors-guide`)
- **Request only the OAuth scopes you approved, and never let config shipped inside untrusted content approve its own servers.** Otherwise the authorization server decides what the agent may reach, and cloning a repo installs whatever it names. Claude Code's `oauth.scopes` restricts a server to a security-approved subset when the authorization server advertises more. In Claude Code, "A cloned repository can't approve its own servers". (`anthropic-docs-claude-code-mcp`)
- **Annotate your own tools honestly, use descriptions as a control, and never trust a name, label or annotation someone else chose.** Codex always asks before a tool that advertises a destructive annotation, unless it also advertises a read annotation. A malicious server that labels a destructive tool read-only skips the gate. Anthropic warns that tool and toolset names are not trust boundaries, and that an absent origin means unknown. OpenAI suggests descriptions like "Do not use to delete records" and regular description reviews. It also suggests logs with correlation IDs instead of raw prompt text, and sharing your best injection prompts with QA so they probe write tools before launch. (`openai-codex-approvals-security`, `anthropic-docs-inference-hooks-endpoint`, `openai-apps-sdk-security-privacy`)

## Pin what you reviewed

- **Read every connected tool's full description, pin names, descriptions and schemas, and diff on any change.** Descriptions are instructions to your model. Invariant (Apr 2025) used hidden text in one to make Cursor send ~/.cursor/mcp.json and SSH keys to a malicious server. Servers can change descriptions after approval (rug pull), mid-conversation included, or shadow trusted tools from other servers. Send your pinned copy instead of re-listing (Anthropic's MCP connector supports it). Cache a list only when its definitions never change. The OpenAI Agents SDK re-lists on every run unless caching is on, and a cached list hides a changed server. (`invariant-tool-poisoning`, `anthropic-docs-mcp-connector`, `openai-agents-sdk-mcp`)
- **Pin plugins to a reviewed commit SHA or archive digest, and skills to a reviewed version whose checksum you verify at deploy.** With auto-update on, "the files you reviewed can change on disk". A marketplace's name tells you who publishes the catalog, not what each plugin does. A production agent that loads the latest skill version runs whatever anyone in the workspace uploads next, with no review. (`anthropic-docs-claude-code-plugins-security`, `anthropic-docs-agent-skills-enterprise`)
- **Govern extensions centrally with required, endorsed and forbidden states per scope, and back them with git so every change is reviewed like code.** Devin Plugins bundle skills, rules, MCP servers, hooks and subagents. Admins can declare each plugin "required, endorsed, or forbidden" at the enterprise, org, repo or individual level, for example hooks that keep agents out of production except for the SRE team (shaped with BlackRock's input, 2026-09-09). Git-backed plugins make changes "versioned, attributable to an author, and reviewed like any other code". Since 2026-10-02 a plugin's skills, MCPs, hooks, rules and dependencies show before install. Devin can also install a plugin from a bare GitHub repository URL (2026-09-11), so decide who approves an install, not only what the preview shows. (`cognition-plugins-blackrock`, `cognition-release-notes-2026`)
- **Pin your agent framework past its security fixes.** OpenAI Agents SDK (Python) v0.23.0 (2026-10-02) enforces Realtime tool output guardrails that weren't enforced before, and scopes function-tool approvals to their owning agent. It redacts default tool failure details and streaming tracebacks, rejects silently discarded tool arguments and requires encrypted session-history envelopes. Earlier, v0.22.3 (2026-09-17) made conditional approvals judge the arguments actually executed, and v0.22.1 (2026-09-08) fails closed on empty arguments. Before these, a voice agent's output guardrails existed on paper only. (`openai-agents-sdk-release-notes`)

## Servers you build or call

- **Authenticate the end user at every MCP server, tunnel or not, and accept only tokens issued for that server.** Transport authentication proves the caller is your agent platform, not that this user may see this record. So require OAuth with per-user authorization even behind a private tunnel. The MCP spec forbids token passthrough. Forwarding a client's token downstream bypasses your rate limits and validation, and breaks the audit trail. It also lets anyone with a stolen token use your server as an exfiltration proxy. (`anthropic-docs-mcp-tunnels-security`, `mcp-spec-security-best-practices`)
- **Never treat a session ID as authentication.** Authenticate every request, and use cryptographically random IDs bound to the user that rotate or expire. The MCP spec documents session hijack prompt injection. An attacker holding a session ID injects events, such as a forged tools-changed notification, that the real client acts on. (`mcp-spec-security-best-practices`, `mcp-security-best-practices`)

## Headless runs, CI and keys

- **Never let anyone on the internet trigger an agent that has shell or package-install tools in CI, and never interpolate their text into its prompt.** In Clinejection (exposed 2025-12-21 to 2026-02-09), Cline's issue-triage bot ran claude-code-action with Bash for any GitHub user. An issue title posing as a "Tool error" made it npm-install attacker code. Actions cache poisoning then pivoted to steal VS Code Marketplace, OpenVSX and npm publish tokens. If it must run, give it read-only tools, no shell, and isolation from the caches and credentials of release workflows. (`khan-clinejection`)
- **In CI and other headless runs, repository-supplied hooks, environment settings and tool servers execute without a prompt, so pass config explicitly.** Under Claude Code's `-p` mode or the SDK, a repository's hooks, env block, key helpers and MCP servers run without asking. Its project settings outrank yours, so a repository can switch a user-level "disable hooks" back on. Inventory tool servers from every source (user scope, hosted connectors, plugins), since the project's server file doesn't show them all. Anthropic "does not security-audit or manage any MCP server". (`anthropic-docs-claude-code-security`, `anthropic-docs-claude-code-permissions`)
- **Never ship a provider API key in a chatbot widget, app, image, website or repo, and give each environment and agent its own key.** Anthropic says stolen keys most often come from customers who exposed them in products, chatbots included. Resellers rotate them through proxies to blend in with the owner's traffic. Keep keys in a secret manager and scan repos. Rotate them (Anthropic suggests every 90 days, 2026-03-16), and watch usage for spikes that aren't yours. (`anthropic-threat-intel-september-2026`, `anthropic-api-key-best-practices`)
- **Protect your LLM gateway's admin credential like a production root key, and monitor its routing and callback config.** Rehberger's LLM Heist (2026-08-03) used only documented LiteLLM admin features. It rerouted models, read every prompt and response, stole provider keys and injected forged tool calls into responses without touching a client. No bug was needed. (`rehberger-litellm-heist`)

## How often MCP attacks work

- **Tool poisoning needs its own tests, because ordinary injection payloads don't reproduce it.** A poisoned description in any connected server steers calls to other, legitimate tools without the poisoned tool being called. Safety alignment targets harmful content, not legitimate tools used for unauthorized operations. InjecAgent's indirect-injection payloads moved into tool descriptions scored 0.1% and 0.0% on Qwen3-8b with and without reasoning. MCPTox's purpose-built descriptions scored 41.8% and 14% (v2 2026-09-29, USTC and Beihang University). (`mcptox-benchmark`)
- **Expect most models to follow a poisoned tool description and almost none to refuse it.** MCPTox (v2 2026-09-29, USTC and Beihang University) covers 45 live MCP servers, 353 real tools and 1,348 cases. Attack success over valid outputs, averaged over 3 paradigms and 3 settings, was 36.5% on average. The highest refusal rate, Claude-3.7-Sonnet's, was less than 3%. (`mcptox-benchmark`)
- **Attacks through MCP tools succeed against every model tested, the newest included.** MCP Security Bench (BUPT and UC Santa Barbara, ICLR 2026, v2 2026-03-24) ran 2,000 attack instances of 12 attack types on real MCP tools. Average attack success across attacks: DeepSeek-V3.1 60.94%, GPT-4o-mini 58.56%, Claude 4 Sonnet 52.51%, Qwen3 8B 47.23%, Llama3.3 70B 46.61%, GPT-5 37.17%, Gemini 2.5 Flash 30.26%, Qwen3 30B 27.14%, Llama3.1 70B 23.37%, overall 40.35%. With MCIP, DeepSeek-V3.1 went from 60.94% to 45.63%. (`msb-mcp-security-bench`)
- **Expect a safety system prompt to help little against MCP attacks, and sometimes hurt.** Prompt-level defenses can't cover threats coupled to the toolchain, and no model was safe overall. MCP-SafetyBench (ICLR 2026, v2 2026-03-05, by its authors) covers 20 attack types in 5 domains. Overall attack success: o4-mini 48.16%, Gemini-2.5-Pro 46.94%, Gemini-2.5-Flash 45.31%, GPT-4.1 42.45%, GPT-4o 42.04%, Grok-4 40.41%, GPT-5 37.55%, Claude-3.7-Sonnet 33.06%, Claude-4.0-Sonnet 31.43%. Host-side attacks (intent injection, identity spoofing) averaged 81.94%, and identity injection worked on 13 of 13 models. The safety prompt raised success by +7.34% for preference manipulation and +9.36% for function overlapping. (`mcp-safetybench`)
- **Fix MCP transport and client security in code, because the choice of model doesn't help there.** Schema inconsistencies, vulnerable clients, MCP rebinding and man-in-the-middle are structural, and prompt- or model-level defenses only touch prompt-based attacks. MCPSecBench (v3 2026-02-12, from Eurecom, Lingnan University, U Oregon and HKUST) runs 17 attack types, 15 trials each. Protocol-side attacks succeeded 100% of the time on Claude Desktop (claude-opus-4.5), OpenAI (GPT-4.1) and Cursor v2.3.29. Use TLS, origin and DNS-rebinding checks, schema validation and patched clients. (`mcpsecbench`)
- **Expect client- and server-side MCP attacks to succeed on every host, with add-on protections catching few of them.** On the same hosts in MCPSecBench, client-side attacks averaged Claude 33.3%, OpenAI 66.7% and Cursor 80%. Server-side attacks averaged Claude 78.1%, OpenAI 75.2% and Cursor 75.2%. The MCIP and FAN protections were "largely ineffective, achieving an average success rate of less than 30%". (`mcpsecbench`)
