# Supply chain: MCP servers, skills, plugins and keys

Every MCP server, skill, plugin and SDK your agent loads runs with the agent's identity, and every tool description is an instruction to your model. Review before you install, expose only the tools you need, pin what you reviewed, and authenticate every call.

## Installing is running someone else's code

- **Treat installing a plugin, skill or MCP server as running someone else's code with your agent's privileges.** Permission rules and the sandbox cover the model's tool calls, "not the code a plugin runs by itself", and an install preview "shows that a hook exists but not what it runs", so read hook commands, server definitions and bundled executables yourself. The MCP spec makes consent MUST-level for one-click local server setup: show the exact command before approval, then run the server sandboxed with minimal file and network access and grant more only explicitly. (`anthropic-docs-claude-code-plugins-security`, `mcp-spec-security-best-practices`)
- **Install skills only from authors you trust, and read every bundled file, scripts and images included, with a tool that shows invisible characters.** A malicious skill can plant vulnerabilities or tell the agent to exfiltrate, and one that fetches external URLs can turn malicious after your audit when that content changes, so reject or re-audit fetching skills. Rehberger (Feb 2026) backdoored a real OpenAI skill with invisible Unicode Tag instructions that Gemini, Claude and Grok follow; scan for Tag codepoints and zero-width characters and strip them from untrusted text before the model sees it. (`anthropic-agent-skills-engineering`, `anthropic-docs-agent-skills-overview`, `rehberger-scary-agent-skills`)
- **A marketplace or vendor scan is not your review.** After ClawHub added VirusTotal and ClawScan, five malicious skills still got through between February and May 2026, one padding its README with 22 MB to exceed scanner size limits (Unit 42, 2026-06-23); Bitdefender found "approximately 17%" of the OpenClaw skills it analyzed malicious (Feb 2026), and Koi found 341 malicious skills on ClawHub the same month. Anthropic's own skill scanning skips skills uploaded through the API or Console, skills that predate it, and CMEK, ZDR and HIPAA orgs, and a pass with a warning stays usable. (`unit42-openclaw-supply-chain`, `rehberger-scary-agent-skills`, `anthropic-docs-agent-skills-enterprise`)
- **Review every component against fixed criteria, and never let the author review their own.** Anthropic's enterprise checklist rates bundled scripts, instructions to ignore safety or hide actions, MCP references, network calls and hardcoded credentials as high risk, and checks file-read plus network tools and read-then-send patterns that leak through the agent's own replies. Its directory rules add that descriptions match behavior, nothing tells the model to call or interfere with other tools (tool shadowing), no instruction is hidden, encoded or fetched at runtime, and the component collects only the data its function needs, never memory or chat history. (`anthropic-docs-agent-skills-enterprise`, `anthropic-software-directory-policy`)
- **Block skills and documents from telling the agent to install a prerequisite.** The ClawHavoc campaign (early 2026) used a fake "prerequisite block" so the agent itself decoded and ran AMOS stealer droppers, auto-updater skills added cron jobs so the C2 survived skill removal, and the C2 still received deliveries three months after disclosure. Route every package install through an allowlisted, human-approved path. (`unit42-openclaw-supply-chain`)
- **Watch for components that steer what the agent recommends without touching data or running code.** Unit 42 found a "money-radar" skill that fetched a remote referrals.json, "approximately 60 products across eight categories", before any financial question and told the agent to always use its affiliate links, changeable after install. Where the agent recommends products, plans or vendors, source the options from your own catalog and log which component introduced each link. (`unit42-openclaw-supply-chain`)

## Expose only the tools you need

- **Validate every input at your tool server "even if the model provided them"** (agent-harness rule 2). The model is a confused deputy: whatever an attacker gets into its context arrives at your server as well-formed arguments. OpenAI's guidance for MCP servers and apps also enforces OAuth scopes on every call (401 on expired or malformed tokens), requires confirmation for irreversible operations, and keeps secrets and tokens out of anything the model or UI component sees. (`openai-apps-sdk-security-privacy`)
- **Drop any tool argument the tool doesn't legitimately need.** On MCP Security Bench (real MCP tools, 2,000 attack instances; ICLR 2026, v2 2026-03-24; BUPT and UC Santa Barbara) the most effective attack was a tool declaring an out-of-scope parameter such as a password, which agents filled 76.5% of the time on average; the tool-invocation stage was the least secure (>70% average attack success), and the MCIP detector lowered attack success but over-rejected and hurt utility. (`msb-mcp-security-bench`)
- **Enable a third-party server's tools by allowlist, and deny by name whatever must never load.** On Anthropic's MCP connector every tool is enabled by default, tools the server adds later turn on automatically, and for a misspelled name in the disable list "a backend warning is logged but no error is returned". The OpenAI Agents SDK filters a server's tools per run, requires approval on sensitive ones by name, and passes tokens in an Authorization header, never the URL. (`anthropic-docs-mcp-connector`, `openai-agents-sdk-mcp`)
- **Re-test tool allowlists and denylists after every platform upgrade, because a release can change what they filter.** From Claude Code v2.1.259 the allowlist stopped filtering centrally managed servers, which started loading with no prompt or notice, so only the denylist still subtracts them. (`anthropic-docs-claude-code-managed-mcp`)
- **Connect to the MCP server the service vendor runs, keep per-call approval on until you've reviewed what it requests, and log every payload you send.** OpenAI's example is Stripe's own `mcp.stripe.com`, not a third-party proxy; third-party servers "may request for data that you may not always be comfortable sharing", may hide injections and "may update tool behavior unexpectedly", and data sent there leaves your ZDR and residency guarantees. (`openai-mcp-connectors-guide`)
- **Request only the OAuth scopes you approved, even when the authorization server advertises more, and never let config shipped inside untrusted content approve its own servers.** Claude Code's `oauth.scopes` restricts a server to a security-approved subset when the authorization server advertises more, and "A cloned repository can't approve its own servers". (`anthropic-docs-claude-code-mcp`)
- **Annotate your own tools honestly, use descriptions as a control, and never trust a name, label or annotation someone else chose.** Codex always asks before a tool that advertises a destructive annotation unless it also advertises a read annotation, so a malicious server that labels a destructive tool read-only skips the gate, and Anthropic warns that tool and toolset names are not trust boundaries and an absent origin means unknown. OpenAI suggests descriptions like "Do not use to delete records", regular description reviews, logs with correlation IDs instead of raw prompt text, and sharing your best injection prompts with QA so they probe write tools before launch. (`openai-codex-approvals-security`, `anthropic-docs-inference-hooks-endpoint`, `openai-apps-sdk-security-privacy`)

## Pin what you reviewed

- **Read every connected tool's full description, pin names, descriptions and schemas, and diff on any change.** Descriptions are instructions to your model: Invariant (Apr 2025) used hidden text in one to make Cursor send ~/.cursor/mcp.json and SSH keys to a malicious server, and servers can change descriptions after approval (rug pull), mid-conversation included, or shadow trusted tools from other servers. Send your pinned copy instead of re-listing (Anthropic's MCP connector supports it), and cache a list only when its definitions never change, since the OpenAI Agents SDK re-lists on every run unless caching is on and a cached list hides a changed server. (`invariant-tool-poisoning`, `anthropic-docs-mcp-connector`, `openai-agents-sdk-mcp`)
- **Pin plugins to a reviewed commit SHA or archive digest, and skills to a reviewed version whose checksum you verify at deploy.** With auto-update on, "the files you reviewed can change on disk", and a marketplace's name tells you who publishes the catalog, not what each plugin does. A production agent that loads the latest skill version runs whatever anyone in the workspace uploads next, with no review. (`anthropic-docs-claude-code-plugins-security`, `anthropic-docs-agent-skills-enterprise`)
- **Pin your agent framework past its security fixes.** OpenAI Agents SDK (Python) v0.23.0 (2026-10-02) enforces Realtime tool output guardrails that weren't enforced before, scopes function-tool approvals to their owning agent, redacts default tool failure details and streaming tracebacks, rejects silently discarded tool arguments and requires encrypted session-history envelopes; v0.22.3 (2026-09-17) made conditional approvals judge the arguments actually executed, and v0.22.1 (2026-09-08) fails closed on empty arguments. Before these, a voice agent's output guardrails existed on paper only. (`openai-agents-sdk-release-notes`)

## Servers you build or call

- **Authenticate the end user at every MCP server, tunnel or not, and accept only tokens issued for that server.** Transport authentication proves the caller is your agent platform, not that this user may see this record, so require OAuth with per-user authorization even behind a private tunnel. Token passthrough is forbidden by the MCP spec: forwarding a client's token downstream bypasses your rate limits and validation, breaks the audit trail, and lets anyone with a stolen token use your server as an exfiltration proxy. (`anthropic-docs-mcp-tunnels-security`, `mcp-spec-security-best-practices`)
- **Never treat a session ID as authentication.** Authenticate every request and use cryptographically random IDs bound to the user that rotate or expire; the MCP spec documents session hijack prompt injection, where an attacker holding a session ID injects events, such as a forged tools-changed notification, that the real client acts on. (`mcp-spec-security-best-practices`, `mcp-security-best-practices`)

## Headless runs, CI and keys

- **Never let anyone on the internet trigger an agent that has shell or package-install tools in CI, and never interpolate their text into its prompt.** Clinejection (exposed 2025-12-21 to 2026-02-09): Cline's issue-triage bot ran claude-code-action with Bash for any GitHub user, an issue title posing as a "Tool error" made it npm-install attacker code, and Actions cache poisoning pivoted to steal VS Code Marketplace, OpenVSX and npm publish tokens. If it must run, give it read-only tools, no shell, and isolation from the caches and credentials of release workflows. (`khan-clinejection`)
- **In CI and other headless runs, repository-supplied hooks, environment settings and tool servers execute without a prompt, so pass config explicitly.** Under Claude Code's `-p` mode or the SDK, a repository's hooks, env block, key helpers and MCP servers run without asking, and its project settings outrank yours, so a user-level "disable hooks" can be switched back on. Inventory tool servers from every source (user scope, hosted connectors, plugins), since the project's server file doesn't show them all, and Anthropic "does not security-audit or manage any MCP server". (`anthropic-docs-claude-code-security`, `anthropic-docs-claude-code-permissions`)
- **Never ship a provider API key in a chatbot widget, app, image, website or repo, and give each environment and agent its own key.** Anthropic says stolen keys most often come from customers who exposed them in products, chatbots included, and resellers rotate them through proxies to blend in with the owner's traffic. Keep keys in a secret manager, scan repos, rotate them (Anthropic suggests every 90 days, 2026-03-16), and watch usage for spikes that aren't yours. (`anthropic-threat-intel-september-2026`, `anthropic-api-key-best-practices`)
- **Protect your LLM gateway's admin credential like a production root key, and monitor its routing and callback config.** Rehberger's LLM Heist (2026-08-03) used only documented LiteLLM admin features to reroute models, read every prompt and response, steal provider keys and inject forged tool calls into responses without touching a client. (`rehberger-litellm-heist`)

## How often MCP attacks work

- **Tool poisoning needs its own tests, because ordinary injection payloads don't reproduce it.** A poisoned description in any connected server steers calls to other, legitimate tools without the poisoned tool being called, and safety alignment targets harmful content, not legitimate tools used for unauthorized operations. InjecAgent's indirect-injection payloads moved into tool descriptions scored 0.1% and 0.0% on Qwen3-8b with and without reasoning, against 41.8% and 14% for MCPTox's purpose-built descriptions (v2 2026-09-29; USTC and Beihang University). (`mcptox-benchmark`)
- **Expect most models to follow a poisoned tool description and almost none to refuse it.** MCPTox (45 live MCP servers, 353 real tools, 1,348 cases; v2 2026-09-29; USTC and Beihang University), attack success over valid outputs averaged over 3 paradigms and 3 settings: average 36.5%, o1-mini 72.8%, DeepSeek-R1 70.9%, Phi-4 70.2%, GPT-4o-mini 61.8%, Gemini-2.5-flash 59.7%, Qwen3-32b (reasoning) 58.5%, DeepSeek-V3 56.5%, Claude-3.7-sonnet 34.3%, GPT-3.5-turbo 14.9%, Mistral 8.3%, and the highest refusal rate, Claude-3.7-Sonnet's, was less than 3%. (`mcptox-benchmark`)
- **Attacks through MCP tools succeed against every model tested, the newest included.** MCP Security Bench (real MCP tools, 2,000 attack instances, 12 attack types; ICLR 2026, v2 2026-03-24; BUPT and UC Santa Barbara), average attack success across attacks: DeepSeek-V3.1 60.94%, GPT-4o-mini 58.56%, Claude 4 Sonnet 52.51%, Qwen3 8B 47.23%, Llama3.3 70B 46.61%, GPT-5 37.17%, Gemini 2.5 Flash 30.26%, Qwen3 30B 27.14%, Llama3.1 70B 23.37%, overall 40.35%, out-of-scope parameter 76.5%; with MCIP, DeepSeek-V3.1 went from 60.94% to 45.63%. (`msb-mcp-security-bench`)
- **Expect a safety system prompt to help little against MCP attacks, and sometimes hurt.** Prompt-level defenses can't cover threats coupled to the toolchain, and no model was safe overall. MCP-SafetyBench (20 attack types, 5 domains; ICLR 2026, v2 2026-03-05; its authors): o4-mini 48.16%, Gemini-2.5-Pro 46.94%, Gemini-2.5-Flash 45.31%, GPT-4.1 42.45%, GPT-4o 42.04%, Grok-4 40.41%, GPT-5 37.55%, Claude-3.7-Sonnet 33.06%, Claude-4.0-Sonnet 31.43%; host-side attacks (intent injection, identity spoofing) averaged 81.94%, identity injection worked on 13 of 13 models, and the safety prompt raised success by +7.34% for preference manipulation and +9.36% for function overlapping. (`mcp-safetybench`)
- **Fix MCP transport and client security in code, because the choice of model doesn't help there.** Schema inconsistencies, vulnerable clients, MCP rebinding and man-in-the-middle are structural, and prompt- or model-level defenses only touch prompt-based attacks. In MCPSecBench (17 attack types, 15 trials each; v3 2026-02-12; Eurecom, Lingnan University, U Oregon, HKUST), protocol-side attacks succeeded 100% of the time on Claude Desktop (claude-opus-4.5), OpenAI (GPT-4.1) and Cursor v2.3.29. Use TLS, origin and DNS-rebinding checks, schema validation and patched clients. (`mcpsecbench`)
- **Expect client- and server-side MCP attacks to succeed on every host, with add-on protections catching few of them.** MCPSecBench, same hosts: client-side averaged Claude 33.3%, OpenAI 66.7%, Cursor 80%, server-side Claude 78.1%, OpenAI 75.2%, Cursor 75.2%, and the MCIP and FAN protections were "largely ineffective, achieving an average success rate of less than 30%". (`mcpsecbench`)
