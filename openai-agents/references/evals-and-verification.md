# Evals and verification

How OpenAI and its guest authors check agent work, both inside a single run and across versions. The sources are engineering posts about Codex and internal agents, cookbooks with worked eval and repair loops, the Agents SDK docs on tracing, a partner guide on measuring guardrails, a partner cookbook on eval-driven design, a 2024 hallucination-guardrail cookbook, a few guest posts from teams using Codex, voice eval guides, security-agent posts, a cross-lab safety eval, two benchmark audits, a post on business evals, two undated Codex guides, and the prompts and skills OpenAI ships in the Codex repo (2026-09-26 snapshot). The recurring ideas: give the agent a way to check itself using the tools humans already trust, grade the trace and not only the answer, turn every correction into a test, and remember that a score measures the whole harness, and sometimes a broken dataset, not the model alone.

## Give the agent a check inside the run

- **Plug the agent into the verification tools you already use instead of letting it invent its own.** At Skyscanner, an MCP bridge let Codex ask the IDE for file problems and run the predefined test, lint and format configurations. A wrong constructor call went from a five-step fix loop (work out how to run tests, run them, parse, fix) to three (generate, ask for problems, fix). The author stopped copy-pasting errors into chat. This is one engineer's observation, not a measurement. (`skyscanner-mcp`)
- **Let the agent see what it built.** Giving a frontend agent browser automation to render pages, test viewports and walk flows "significantly improves the likelihood" of polished, complete results, and with image understanding it can compare against a reference. (`frontends`)
- **Build instruments for work judged by feel.** For a space game, the agent got an in-page state interface (current body, flight mode, terrain readiness, draw calls), named test scenes to jump to, and browser tests that load a scene, screenshot it and check state. (`astra-games`)
- **A shortcut to the state is not a test of the path.** Separate journey tests drove the real controls and recorded positions, catching a collision surface that wasn't ready and a ship jumping between positions, which a screenshot of the landing scene would miss. (`astra-games`)
- **Require reviewable artifacts and give the agent tools to validate them before it answers.** A diligence agent writes a memo, risk register, citations and an evidence table, and two workspace tools check that claims cite real source files and that the artifacts exist with the right shape. (`improvement-loop`)
- **A valid shape is not a true answer, so check it against your own record.** A paying agent's structured answer is compared field by field (receipt ID, amount, supplier) with the purchase the app recorded, and tests prove each control says no: an unapproved request is denied before any charge, a fabricated receipt ID is rejected (`agentic-commerce`). A fabricated amount can cite real transaction IDs, so an AML validator recomputes each finding from deterministic code instead of only checking the IDs exist. Worked examples, no measurement. (`agentic-commerce`, `aml-agent`)
- **Give goals the agent can verify.** "Implement the plan in this file" is weak. "Port the library, keep the API compatible, done when the original unit tests pass and differences are documented" is strong. The Codex guide makes "done when" one of four parts of every task prompt, with goal, context and constraints. (`codex-maxxing`, `codex-best-practices`)
- **Completion is a claim to prove, not a failure to find more work.** Codex's shipped goal prompt (`codex-rs/ext/goal/templates/goals/continuation.md`) requires a completion audit: derive concrete requirements from the objective, map each to authoritative evidence, grade it as proves, contradicts, incomplete, too weak or missing, and treat uncertain evidence as not achieved. Tests and green checks count only once they are confirmed to cover the requirement (`repo-goals`). The Goals cookbook adds that hitting the budget is not finishing: the agent stops and reports progress, blockers and the next useful step (`codex-goals`).
- **A long objective needs a finish line, not a bigger prompt.** The Goals cookbook names six parts: outcome, verification surface (test, benchmark, artifact), constraints that must not regress, file and tool boundaries, an iteration policy, and a blocked stop condition saying what to report when no defensible path remains. With "p95 below 120 ms on the checkout benchmark, correctness suite green", 135 ms is not done and 119 ms with failing tests is not done. "Improve the whole system" has no audit surface. (`codex-goals`)
- **For research, fix the evidence standard first and report per claim.** Reproducing the Deep Hedging paper, the goal asked for a claim inventory mapped to evidence. Codex reproduced the Heston reference price and the transaction-cost slope, but missing seeds, training paths and checkpoints blocked exact replay, so the honest result was a partial reproduction with status and uncertainty per claim. One worked example. (`codex-goals`)
- **Guard the check against being gamed.** The same goal prompt bans swapping in a "narrower, safer, smaller ... or easier-to-test solution" because it passes current tests (`repo-goals`). Codex's shipped `babysit-pr` skill forbids "fixing" unrelated CI failures by editing tests, CI config or dependency pins (`repo-skills`). The AI-native team guide writes tests in a separate session from the implementation, checks they fail first, and reviews generated tests for shortcuts or stubs (`ai-native-team`).
- **Verification tooling is what makes risky self-directed work safe to accept.** When a model rewrote production GPU kernels for a 20% serving cost cut, a floating-point sanitizer was the guard on correctness. (`gpt56-efficiency`)
- **An agent that notices a suspicious intermediate result should investigate before reporting.** The data agent treats zero rows from a bad join or filter as a signal to adjust and retry, instead of handing iteration back to the user. (`data-agent`)

## Repair loops: separate judgment from proof

- **Split the loop into review, repair and validate, and never let the repairer grade itself.** Review reads and returns findings without editing. Repair edits a copy from those findings plus the last validation feedback, and its prompt says "Do not claim the notebook passes validation". Validation decides. The worked example fixes stale docs notebooks, but the authors say it fits any output with trustworthy feedback (`repair-loops`). In a security workflow, an independent validator that treats upstream labels as hypotheses turned 10 scanner candidates into 6 confirmed, 2 not actionable and 2 needing review, in one run (`security-scanners`).
- **"Confirmed" means no proof gap is left, and a model can't clear one.** A proof gap is a missing fact that could change the judgment. An unknown that doesn't change what the source shows (deployment, exposure) is only a limitation. Code carries a specialist's gaps forward even if the validator disagrees, so a JWT decoded without a signature check, but after a call to a verifier outside the approved files, stayed "needs review". (`security-scanners`)
- **Run the artifact before judging it.** A missing import, a stale path or an old API response shape only shows at runtime, so each notebook runs end to end before a judge scores three named cases, and an execution failure fails the whole pass. Elsewhere validation could be a unit test, policy check, schema validator, simulation or human approval. (`repair-loops`)
- **Phases pass structured results and share one contract of "good".** Findings (type, severity, direction), changes plus unresolved items, and per-case pass or fail with evidence and a "remaining delta" go straight into the next prompt "instead of scraping prose". A small business-rules object (current API targets, preferred models, "preserve the original teaching goal") goes to all three phases, so the judge doesn't flag the preferred models as stale. (`repair-loops`)
- **Watch the delta shrink, and write the stop conditions.** Later passes ask for "the smallest useful edits". Stop when validation passes, attempts run out, the delta stops changing, or the next decision needs a human, and keep a per-pass receipt of what was found, changed, run and left. The demo fixtures were built to clear in one, two and three passes, so it shows the mechanism, not a result. (`repair-loops`)

## Build evals for skills and agents

- **Without evals you can't tell improving a skill from just changing it.** An eval is a prompt, a captured run (trace plus artifacts), a small set of checks and a comparable score. Otherwise a regression slips in unnoticed: the skill doesn't trigger, skips a step, or leaves extra files. (`eval-skills`)
- **Define success before writing the skill, in four kinds of goal.** Outcome (did it work), process (did it follow the intended steps), style (conventions) and efficiency (no thrashing). "Without clear constraints, there's nothing concrete to evaluate." (`eval-skills`)
- **Frontier benchmarks don't cover your workflow, so the people who own it specify "great".** A small cross-functional team maps each decision point and writes a golden set of dozens of expert input-to-output examples. Measure in an environment that mirrors production, with rare but costly edge cases added, and watch for rubrics that over-weight superficial items. (`business-evals`)
- **Price each eval failure in money and work back from the decision.** A partner cookbook modeled receipt auditing (1 million receipts a year, $2 per audit, $30 per missed one). Merchant names were wrong 85% of the time yet never changed an audit decision, while missing a handwritten "X" about half the time could cost about $75,000 a year: "not all evals matter". With no ground truth, a v0 system drafts labels for experts to correct, and inputs where repeated runs or different models disagree get labeled first. 20 samples, hypothetical costs. (`eval-driven-design`)
- **Run it by hand first, then turn every manual fix into a test.** Manual runs expose triggering, environment and execution assumptions. 10 to 20 prompts are enough for one skill if they include explicit, implicit and noisy invocations plus negative controls that should not trigger it (`eval-skills`). Without negatives you reward shortcuts: a voice support bot scored 98% offline on "escalate to human", then escalated almost everything in dogfooding, because the set had almost no do-not-escalate cases (`realtime-evals`). For a business workflow, start by reviewing 50 to 100 prototype outputs into an error taxonomy with frequencies (`business-evals`).
- **Validate a skill by behavior, and forward-test it blind.** Codex's shipped skill-creator says a structural validator "does not prove that the skill makes good decisions", so tests check observable behavior, not headings or regex matches. Risky skills get an independent sub-agent with a realistic request, minimal artifacts, no intended answer and an isolated workspace. (`repo-skills`)
- **Grade what the agent did, not only the final output.** Deterministic checks over the event trace (did it install, which commands in what order) tell you exactly why something failed. Add a model grader for qualitative checks, forced to return structured JSON so results diff across runs, and add heavier checks (token use, smoke tests, clean git status) only where they reduce risk (`eval-skills`). OpenAI's API docs stack this trace grading, scoring specific decisions, tool calls and reasoning steps, on top of input guardrails (`docs-agent-safety`). Carlyle credits OpenAI's trace-grading evals with over 50% less development time and 30% higher accuracy on a multi-agent diligence framework, a customer quote (`agentkit`).
- **Record the run as nested spans under one workflow trace.** Every model call, tool call, handoff and guardrail is a timed span. Several agent calls that form one logical workflow share a trace, and a conversation id links traces across turns. By default the trace holds model and tool inputs and outputs, so it is sensitive data. (`sdk-tracing`)
- **Test agent behavior end to end.** The Codex team's own `AGENTS.md` says "Features that change the agent logic MUST add an integration test", preferring integration over unit tests, with a mocked model server and assertions on the outbound request bodies (`repo-agents-md`). The SDK docs draw the line where ownership changes: a scripted model tests the loop, tools, guardrails and retries you own, while whether a real model picks the right command, and what a real sandbox or audio model does, stay in integration tests (`sdk-testing`).
- **Evals can be continuous unit tests against golden answers.** The data agent keeps question plus golden SQL pairs, executes the generated SQL, and grades both query and result data with a grader that tolerates syntactic variation and extra columns. "Without a tight feedback loop, regressions are inevitable and invisible." (`data-agent`)
- **Gate on quality before looking at cost.** Policy compliance, action correctness, security and escalation accuracy are hard gates, run on a stratified eval set (intent, risk, language, region, edge cases) plus a holdout. (`cost-quality`)
- **Read trajectories and calibrate the judge.** Traces reveal loops and wrong actions a polished answer hides. The judge checks grounding against recorded tool results ("your refund is on its way" fails if only a review case was opened), never overrides a deterministic failure, and is checked against a small hand-labeled sample first (`cost-quality`). The domain expert keeps auditing the grader and reading the logs directly after that (`business-evals`). One large company's executives listened to about 3 hours of voice sessions a day and found early cutoffs and phantom interruptions offline evals missed (`realtime-evals`). In a cross-lab safety eval, manual review found most of an apparent gap between two model families was grader error on nuanced refusals (`oai-anthropic-eval`).
- **Keep three sets so the suite can't silently overfit.** A regression suite of fixed hard cases runs on every prompt, model and tool change. A rolling discovery set takes fresh production failures and near misses and promotes the ones that expose a failure mode. A holdout stays untouched: "If test scores climb while holdout stays flat, you are training for the test." (`realtime-evals`)
- **When a front delegates to a backend, grade each boundary, and let only task completion gate.** "A natural-sounding confirmation does not prove the correct backend actions were completed", so check delegation, the tool call and its arguments, the resulting app state, and that the result was reported only after the tool succeeded. A run passed with 50% tool accuracy, because tool and delegation scores diagnose and mandatory steps must be marked critical to gate. Classify each failure as the assistant, the infrastructure or the grader before changing anything: a 75% response rate was a farewell counted twice (`voice-evals`). For voice, the transcript is a model's reading of the audio, so audit about 1 to 5% of sessions from the audio itself (`realtime-evals`).
- **Repeat nondeterministic runs and report the spread.** Voice scenarios are repeated and reported as P50 and P90 with sample counts (`voice-evals`). Apollo's 13 scheming environments ran 100 times each, and because outliers dominated the averages, results also count environments at exactly 0, below 0.05 and below 0.5 (`oai-anthropic-eval`).
- **To improve a multi-agent system, look across traces, not only within one.** Compress each run into a short digest (outcome, handoffs, specialist activations, review markers), cluster the digests into recurring patterns, rank them by prevalence times severity, then find the slice (scenario, agent version, orchestration mode) where each concentrates. Walking back from a failure ranks upstream suspects to inspect, "not proof of causality". A partner method on 1,000 synthetic runs, no result. (`macro-evals`)
- **Measure guardrails like classifiers, with the exact config you deploy.** Precision counts legitimate queries blocked, recall counts threats missed, and conversation-aware test cases carry the real system prompt. Every guardrail scored 100% on a 21-sample set, which is small. An automated tuning loop moved the jailbreak threshold from 0.95 to 0.90 and recall from 0.75 to 1.0 in one step, but off-topic stayed at zero precision and recall through five steps, so tuning helps only where the threshold is the problem, in a partner cookbook (`governance`). A 2024 cookbook's hallucination check scored each sentence 0 or 1 on four criteria, cited the knowledge-base line for every pass, and reached 0.97 precision and 1.00 recall, but on synthetic conversations from the same model family (`hallucination-guardrails`).
- **Detection accuracy and bypass resistance are different tests.** A labeled eval asks whether the guardrail fired. Red teaming asks whether an attacker gets through, with generated, adaptive attacks (encodings, escalating multi-turn, prompt extraction) graded by a model. The demo blocked 33 of 33 probes, and the authors advise 50 or more per attack type in production. (`governance`)
- **Use an agent as a proxy reader to test docs coverage.** Give it only the docs, have it build a project, run a test suite on the result. If it works, coverage is adequate. The authors call this experimental. (`dagster-docs`)
- **Simulate users at volume.** Hexagon runs thousands of realistic shopping prompts a day, varying region and reasoning depth, to track how answers behave. Raindrop evaluates production agents continuously against developer-set failure conditions and traces a failure to the prompt or system change that caused it. (`responses-year`)

## Corrections become evals

- **Optimize the harness, not just the prompt.** The harness (instructions, tools, routing, output requirements, validation) is an explicit, versioned config. Traces show what happened, feedback says what mattered, evals make it reusable, and a coding agent turns the evidence into a ranked change set (`improvement-loop`). A Codex cookbook ends each project with a read-only retrospective that routes every lesson to exactly one owner (repo instructions, a skill, a validator when the check is mechanical, a regression test when it reproduces, or no change) and won't "manufacture a root cause when evidence supports only a symptom" (`codex-iterating`).
- **Seed test data with deliberate conflicts.** A synthetic dataroom mixed exports with narratives that disagree ("SOC 2 complete" when only Type I exists, a management estimate that contradicts finance data) to surface real failure modes. (`improvement-loop`)
- **Keep expert feedback and model feedback separate, and have humans vet generated evals.** Model feedback widens coverage and expert feedback carries domain judgment. Generated evals mix literal assertions with a rubric judge, and people check they measure what matters before they join the suite. (`improvement-loop`)
- **A passing gate is not the end.** All 5 generated evals passed, yet the diagnosis found validators could pass while citation problems remained in the actual artifacts. (`improvement-loop`)
- **Move the human gate as trust grows.** Start with the system proposing a diff that a developer approves, then close the loop once the eval gate earns trust. Gates can sit at trace review, eval refinement, PR, merge or deploy. (`improvement-loop`)
- **Turn expert corrections into eval targets in three steps.** Capture the diff between what the agent proposed and what the expert filed, group related failures to separate recurring product bugs from noise, and promote repeated patterns to targets. (`tax-agents`)
- **Hand the coding agent a scoped task, not an alert.** Its environment splits a writable worktree (product code, targeted and regression evals, skills) from read-only production evidence (trace, source documents, prediction, final return). It diagnoses, fixes, reruns evals and proposes a PR for review. Returns reaching 75% correct field completion went from about a quarter at launch to 86% in six weeks (`tax-agents`). A security workflow has code, not a model, render that task in under 4,000 characters from confirmed findings only, ending with "Stop and ask for review if the pinned source no longer matches the evidence above" (`security-scanners`).
- **Evals don't stop at launch.** Log inputs, outputs and outcomes, sample on a schedule, route ambiguous or costly cases to experts, and add their judgments to the eval. Evals decay as models, data and goals change, and for external products they sit next to A/B tests, not in place of them (`business-evals`). A partner pipeline versions its prompts, re-runs sampled production inputs through alternatives, and rolls back when a tracked metric crosses a threshold such as 90% accuracy (`temporal-agents`).
- **Quality is a loop: eval, improve, re-eval.** Programmable graders make it repeatable, and a task validated on a large model can then be distilled into a cheaper one. (`devs-2025`)

## Review agents

- **Written review rules measurably raise recall of team-specific bugs.** On a suite of known violations plus safe counterexamples, rule-guided review recovered 98% of required custom findings versus 58.3% for the baseline. Some bugs are invisible in the diff, like renaming an event that compiles but breaks a downstream consumer. (`review-rules`)
- **Score a reviewer on four axes, not just recall.** Coverage (finds violations in busy diffs), restraint (no finding on clean changes and valid exceptions), retention (still catches ordinary bugs), actionability (each finding names guidance, location, priority). (`review-rules`)
- **Test each rule with three cases.** One change that should trigger it, one safe counterexample, one unrelated change. Rules complement CI, linters and required approvals, they don't replace them. (`review-rules`)
- **Codex's shipped rubric flags only what the author would fix.** `codex-rs/prompts/templates/review/rubric.md` requires real impact, a discrete fix, a bug introduced by this change, and the provably affected code named. It prefers zero findings over invented ones ("Do not invent a finding to fill the result") but forbids stopping at the first. That is the restraint axis above, in shipped form. (`repo-review`)
- **Findings carry severity, confidence and a verdict.** Each has P0 to P3 (P0 only when it depends on no input assumptions), a confidence from 0 to 1 and a 5 to 10 line range on the diff, and the review ends with a correct or incorrect verdict that ignores style. The general Codex prompts also put findings first, by severity, and say so when there are none. (`repo-review`, `repo-system-prompts`)
- **Breadth comes from fan-out, and rule citations must be earned.** The shipped `code-review` skill spawns one sub-agent per narrow review skill at the highest reasoning effort and returns every issue. A finding counts as rule-supported only when the rule adds something beyond generic correctness, citing its smallest line range. The reviewer is read-only and checks each finding against tests and call sites. (`repo-review`)
- **A reviewer has to be high-signal or it gets ignored.** "Overly verbose responses are ignored just as easily as noisy lint warnings", and general models "often nitpick", so tune for P0 and P1 bugs. Evaluate against a curated set of gold-standard human PR reviews, and use comment reactions as a cheap signal. AI review prevents defects more than it speeds PRs up. (`ai-native-team`)
- **Prove a finding by running it before a human triages it.** Aardvark builds a threat model of the whole repo, checks each commit against it, and tries to trigger each suspected vulnerability in a sandbox, then rescans the proposed patch. OpenAI claims 92% recall on repos seeded with known bugs, a launch claim with no method (`aardvark`). Codex Security tries to falsify each apparent defense on the smallest testable slice, with micro-fuzzers or a z3 solver, because the hard bugs are defenses that don't hold, not missing dataflow: "There's no better proof than a full end-to-end PoC" (`codex-security-sast`).

## Evals measure harnesses, and benchmarks break

- **A benchmark scores a bundle of harness, settings and prompting.** On ARC-AGI-3, keeping past reasoning and compacting instead of truncating took the same model from 13.3% to 38.3% with about 6x fewer output tokens. OpenAI had been surprised before by low scores from eval runners that dropped reasoning (`arc-agi-3`, `codex-platform`). Test with the tools you deploy and score refusals apart from errors: with browsing off, OpenAI's models, tuned assuming it was on, answered almost everything and hallucinated more, while the other lab's models refused up to 70%, at a similar correct-to-incorrect ratio (`oai-anthropic-eval`).
- **Change one thing per rung when swapping models.** Codex's bundled upgrade guide (`references/upgrading-to-gpt-6-astra.md`) validates a migration as a ladder: old model and prompt, new model with the same prompt and effort, one lower effort, the smallest fix for a measured failure, then optional features alone. The metric is total cost per successful task. Failures are never fixed by weakening schemas or dropping tools. (`repo-prompting`)
- **A plateau is a cue to audit the dataset.** SWE-bench Verified crept from 74.9% to 80.9% in six months. Of 138 problems o3 didn't reliably solve in 64 runs, each checked by at least six engineers, 59.4% had material issues: 35.5% narrow tests enforcing unstated implementation details, 18.8% wide tests checking unrequested behavior. Three-reviewer curation (1,699 down to 500) hadn't removed them. (`swe-bench-verified`)
- **Public benchmarks leak into training.** Every frontier model tested could reproduce gold patches or verbatim task details for some tasks, and exposed models passed underspecified tests more often. Probe with an automated red-teamer plus judges and human review, and post with password protection and canary strings. Good tests check behavior and ignore unimportant implementation details. (`swe-bench-verified`)
- **Tasks mined from repos break in four ways.** Overly strict tests, underspecified prompts, low-coverage tests, misleading prompts. The root cause is that issues and PR tests were made for people collaborating, not for grading. About 30% of SWE-Bench Pro is broken (27.4% flagged by the pipeline, 34.1% by humans), so OpenAI stopped recommending it and calls for new benchmarks written by experienced developers specifically for testing models. (`coding-evals-noise`)
- **Audit evals with a funnel, and expect agents to be conservative.** An automated filter flagged 286 tasks, investigator agents ran tests and inspected files in repeated independent passes, and a researcher made the call, while five engineers per task judged in parallel. Humans marked more tasks broken, most of all low-coverage tests (9.4% versus 4.1%). Stronger models make such audits affordable at scale. (`coding-evals-noise`)

## Where the answer depends on the case

- **Finding new security bugs: don't seed the agent with a scanner's findings (2026-03-16).** A findings list narrows the search to where the tool already looked, shifts the agent "from 'investigate' to 'confirm or dismiss'", and makes it impossible to tell what the agent discovered from what it inherited. Precomputed findings still help for narrow, known bug classes. (`codex-security-sast`)
- **Triaging what scanners already flagged: start from their candidates (2026-08-05).** Semgrep and Bandit hits are routed to specialist reviewers, treated as "hypotheses, not proof", and only findings with no open proof gap reach the coding agent. (`security-scanners`)
