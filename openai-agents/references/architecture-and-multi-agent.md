# Architecture and multi-agent systems

Whether to build an agent at all, what one is made of, when to split work across agents, and how to orchestrate many of them. OpenAI's 2025 guide sets the default (one agent in a loop, split only when real failures demand it), and the 2026 posts stretch the same idea to parallel subagents and to a task tracker that keeps an agent running on every open ticket. Drawn from the 2025 PDF guide, engineering posts on openai.com, and developer blog posts, including customer stories without numbers, the Agents SDK docs and cookbook guides, OpenAI's customer-service sample repo, plus the Codex repo (a 2026-09-26 snapshot), which shows the delegation rules OpenAI actually ships in its prompts and tool specs.

## Decide whether you need an agent

- **An agent is a model that controls the workflow, not an app that calls a model.** It decides the steps, knows when it's done, corrects itself, hands control back to the user when it fails, and picks tools inside guardrails. Chatbots, single-turn calls, and classifiers are not agents. (`practical-guide`)
- **Reserve agents for work that resisted automation.** Three signals: nuanced judgment with exceptions (refund approval), rulesets too tangled to maintain (vendor security reviews), and heavy unstructured data (insurance claims). A fraud rules engine is a checklist, an agent is an investigator. Otherwise deterministic code may be enough. (`practical-guide`)
- **The 2025 shift was from prompting step by step to delegating whole tasks.** Better planning and longer tool use moved teams from single requests to handing over jobs, so building agents became "as much about system design (async + events + budgets) as prompting". Codex's team guide ties the shift to task length: citing METR (August 2025), leading models held about 2 hours 17 minutes of work at 50% confidence, a length doubling roughly every seven months. Second-hand, not OpenAI's measurement. (`devs-2025`, `ai-native-team`)

## Model, tools, instructions

- **Every agent is built from the same three parts.** A model, tools, and instructions. Tools come in three kinds: data, action, and orchestration, where other agents are themselves tools. (`practical-guide`)
- **Draft instructions from the policies you already have.** Help-center articles and policies are the raw material, and a strong model can draft the instructions from them (`practical-guide`). Write them as goals, not step-by-step routines (see context-engineering.md).
- **Use one templated prompt with policy variables instead of many prompts.** It keeps a growing set of use cases maintainable before any split is needed. (`practical-guide`)

## Single agent first

- **Maximize one agent before adding more.** Each agent is a loop that runs until an exit condition: a final-output tool, a reply with no tool call, an error, or a turn limit. Split only when the logic has too many if-then branches or the tools overlap, and try better tool names first (see tool-design.md). (`practical-guide`)
- **Merge two agents when users can't tell which one to pick.** OpenAI kept a browser-acting agent and a research agent as separate products until it saw that "many queries users attempted with Operator were actually better suited for deep research". It unified them into one agent with both toolsets on one computer. (`chatgpt-agent`)
- **Let evidence pick the architecture.** At a DevDay booth demo, the agent wrote evals to choose a model trading speed for quality, compared single-agent and multi-agent designs, and refactored to a single agent. One demo, not a study. (`codex-devday`)

## Multi-agent shapes

- **Decide who orchestrates: the model or your code.** Let the model plan open-ended tasks, and fix the flow in code when you need predictable speed, cost, and performance. They mix freely. The code patterns: classify with structured output and route in code, chain agents where each output feeds the next, loop a worker against an evaluator until it passes, and run independent agents in parallel. OpenAI's own tooling moved toward code: on 2026-06-03 it announced it would wind down its visual workflow builder (launched 2025-10-06) by 2026-11-30, sending workflows that "should continue as code" to its SDK. In mixed designs, code keeps what must hold: in a security-review cookbook the manager picks a specialist per candidate, but code checks that every candidate was reviewed exactly once before the run may end. A schema-change pipeline runs deterministic gates after each typed stage so a defect can be traced to the stage where it started. Worked examples, no measurements. (`sdk-multi-agent`, `agentkit`, `security-scanners`, `schemaflow`)
- **Manager or handoff.** In the manager pattern a central agent calls specialists as tools and keeps the user, which fits when one voice should synthesize or shared checks should run in one place. In the decentralized pattern one agent hands off execution and conversation state to a peer for good, which fits triage where a specialist fully takes over. The SDK docs and OpenAI's migration guide frame the choice as who owns the final answer, and a specialist reached by handoff can still call other agents as tools. (`practical-guide`, `sdk-multi-agent`, `claude-sdk-migration`)
- **A handoff forwards the whole conversation unless you narrow it, and narrowing is not redaction.** To the model each destination is one more transfer tool. The receiver inherits the full transcript by default, and filtering or summarizing it is an explicit step. Tool arguments and outputs can survive inside a generated summary, so treat the receiver and its model provider as recipients of the forwarded history. With server-managed history there is nothing to filter, so start a separate run with chosen input. A common split hands off from a plain intake agent to a sandboxed one only for the part that needs isolation. OpenAI's airline sample repo also feeds state forward on purpose: each specialist's instructions are filled with the known booking details so it acts "without re-asking", chains its own tool calls, and emits at most one handoff per message, with a stated order for the next. A demo, no measurement. (`sdk-handoffs`, `sdk-sandbox`, `repo-cs-agents`)
- **An agent called as a tool starts a nested run, so shape what goes in and what comes out.** It gets its own turn loop and turn limit, which don't count against the outer run, and it doesn't inherit the conversation. Give it a structured input instead of one free-text string, and extract its output (just the payload, or a fallback when it's malformed) before the orchestrator sees it. (`sdk-sandbox`, `sdk-tools`)
- **Behind a router, the routing description is the switch.** A partner guide argues one agent holding every domain gets unwieldy instructions, "struggles to stay in character", and can't change one domain without touching the others. A triage agent hands off to specialists, and each specialist's routing description is what the router decides on. Argued, not measured. (`governance`)
- **Keep the worker and the judge apart, and pass structured results.** OpenAI's repair-loop cookbook splits review (findings only, no edits), repair (edits a copy, told "Do not claim the notebook passes validation"), and validation (runs the checks). Each phase returns fields, not prose, and the loop stops when validation passes, attempts run out, the remaining failures stop shrinking, or a human must decide. The demo fixtures were built to clear in one, two, and three passes, so it shows the mechanism, not a result. (`repair-loops`)
- **Separate gathering context from reasoning over it.** Repo Prompt runs a context-builder agent with tools that produces a structured context package, hands it to a reasoning model that makes no tool calls, and lets a reviewer agent decide whether another cycle is needed. A customer story, no numbers. (`responses-year`)
- **Decouple the fast part from the slow part.** In GPT-Live a voice model holds the conversation while it delegates deeper reasoning and tool use to a frontier model in the background. It can keep the exchange moving for a while, but it can't hide an arbitrarily slow result. Codex's shipped realtime prompt (`codex-rs/prompts/templates/realtime/backend_prompt.md`) does the same and hides the split: the voice model presents all work as its own, delegates whenever unsure, and never refuses, because the backend makes the final call on what is doable or safe and the user could reach it directly anyway. (`gpt-live`, `repo-realtime`)
- **Use parallel subagents for parallelizable work, and say when to spawn them.** A primary agent delegates, subagents work in parallel and return output for synthesis. Spawning is steerable, so telling the model when to use subagents keeps the extra token spend to cases where it helps. Each subagent keeps its own context so it stays focused, a product claim with no numbers. In the SDK, though, an agent called as a tool shares the run's app state, approval state, and usage tracking unless you isolate it. (`gpt56-guide`, `agents-api`, `sdk-context`)

## Delegation rules Codex ships

- **Plan the critical path before delegating.** Codex's `spawn_agent` description (`codex-rs/core/src/tools/handlers/multi_agents_spec.rs`) has the agent do the blocking step itself, delegate bounded "sidecar" tasks, give parallel code-editing workers disjoint write sets, and not redo delegated work. "Do not repeatedly wait by reflex." Children inherit the parent's model unless the user asks for another. (`repo-tools`)
- **Once work is delegated, the parent only coordinates.** The orchestrator template (`codex-rs/core/templates/agents/orchestrator.md`) assigns one sub-agent per plan step when it can and waits for them before yielding, but answers a direct user question first. (`repo-multi-agent`)
- **Tell every sub-agent three things.** It is not alone and must not revert others' work, whether it may spawn agents of its own (it has the same tools), and, for a long-running helper, that it can't, to prevent infinite recursion. Good uses: separate scopes, a fresh-context review, offloading noisy test logs. Not simple tasks. Codex's guide adds one chat per coherent unit of work, with sub-agents for bounded side work like exploration or triage. (`repo-multi-agent`, `codex-best-practices`)
- **Sub-agent tooling moved from ids to a named tree with a mailbox.** v1 addressed agents by id, forked context all or nothing, and returned final statuses from a wait. v2 uses hierarchical task names (`/root/task1/task_3`), lets children spawn their own, forks none, all, or the last N turns, and a wait returns only which agents have updates. New tools message, follow up on, interrupt, and list agents. Messages between agents share one envelope: type, task name, sender, payload. (`repo-tools`, `repo-context`)

## Parallel agents and the human bottleneck

- **Best-of-N makes design cheap, and the agent can pick the winner.** At DevDay, a redesigned 404 page shipped from two attempts reviewed in five minutes. ChatGPT agent solves the same task differently across runs, and running up to eight attempts and keeping the one with the highest self-reported confidence raised Humanity's Last Exam from 41.6 to 44.4 pass@1. (`codex-devday`, `chatgpt-agent`)
- **Parallel sessions bring coordination overhead back.** Building Sora for Android, several sessions (playback, search, error handling, tests) felt like leading a team, and the bottleneck moved from writing code to deciding, giving feedback, and integrating. No linear speedup, per Brooks: "Codex didn't get blocked by context switching, but we did." (`sora-android`)
- **Interactive supervision tops out at three to five sessions.** Past that, engineers forgot which session did what and spent their time nudging stalled agents. "The agents were fast, but we had a system bottleneck: human attention." (`symphony`)

## Orchestration: the tracker as control plane

- **Organize around deliverables, not sessions or PRs.** In Symphony every open issue gets its own workspace and an agent that runs until the work is done, and the orchestrator restarts crashed or stalled agents and picks up new issues. One issue can produce several PRs or just an analysis. Landed PRs rose 500% on some teams in the first three weeks, an early internal number. A migration cookbook uses the same unit: one fresh sandbox per repo shard, each mapped to its own PR, because "one massive migration PR is hard to review and risky to merge". (`symphony`, `code-migration`)
- **Big tickets become task trees with dependencies.** An agent writes an implementation plan, then generates the task tree, and agents start only unblocked tasks (the React upgrade waited on the Vite migration). Agents file follow-up issues for improvements outside their scope. (`symphony`)
- **Give objectives, not state-machine transitions.** Early versions only asked for implementation. With a GitHub CLI and CI-log skills the agent also answered review feedback, closed stale PRs, and reported abandoned work: "Give them tools and context and let them cook." (`symphony`)
- **When an agent misses, fix the system, not the output.** Without mid-run steering, the team added guardrails and skills (end-to-end tests, driving the app through browser devtools, QA smoke tests) and wrote down what good looks like. Ambiguous, judgment-heavy work still goes to interactive sessions. (`symphony`)
- **Write the implicit team process down as a versioned workflow file.** Check out, mark in progress, link the PR, move to review, attach a video: humans did it but never documented it. The orchestrator itself is only a spec, and the first version was a single agent in tmux polling the tracker. (`symphony`)
- **Orchestrator mechanics worth copying.** One authoritative state, bounded concurrency, stall detection that kills and retries silent workers, exponential backoff, stopping a run when its ticket leaves an active state, prompts that know whether this is a first run, a continuation, or a retry, one sanitized workspace per agent, restart recovery without a database, and secrets exposed as a tool instead of a token. Implementing the spec in six languages exposed its ambiguities. (`symphony`)

## Where the answer depends on the case

- **How readily to spawn sub-agents: the sources describe different modes.** Spawning is steerable, and the GPT-5.6 guide says to prompt for it where it helps (`gpt56-guide`). Codex ships both settings: its v1 `spawn_agent` description forbids spawning unless the user or instruction files ask, since "requests for depth, thoroughness, research... do not count as permission" (`repo-tools`), while its orchestrator template prefers several sub-agents (`repo-multi-agent`).
