# Safety and containment

How OpenAI bounds what an agent can do: sandboxes, network and secret handling, approvals, prompt injection, guardrails, and monitoring agents after the fact. Most sources are OpenAI engineering posts about running Codex, the Atlas browser and ChatGPT, plus the 2025 practical guide, posts on prompt injection, link safety and monitoring, the Agents SDK and API docs on guardrails and human review, a partner guide on guardrail governance, a guide to a policy-following safety classifier, cookbooks on regulated and paying agents, a cross-lab safety eval, and the approval and context prompts OpenAI ships in the Codex repo (2026-09-26 snapshot). The shared stance: assume the agent will sometimes be fooled or overeager, so limit the damage with deterministic boundaries instead of trusting the model or an input filter.

## Constrain what a manipulated agent can do

- **Real prompt injection looks like social engineering, not a string override.** Early attacks planted instructions in a wiki page and worked on models without adversarial training. As models got smarter, attackers added manipulation (`injection-design`). It is phishing aimed at the model, arriving through third-party content in context (a web page, a listing review, an email), not from the user (`prompt-injections`). In a cross-lab test, all 7 models resisted far-fetched role changes, but believable ones with authority or urgency beat at least 5 of 7, and the calmest, most matter-of-fact prompt fooled all but one (`oai-anthropic-eval`).
- **Input classifiers miss fully developed attacks.** Detecting them becomes as hard as detecting a lie, often without the context needed (`injection-design`). OpenAI still runs AI monitors that block known attacks, since they can be updated faster than training (`prompt-injections`).
- **Keep untrusted text out of privileged instructions and out of free-text channels.** Developer messages outrank user ones, so untrusted input goes in as a user message. Between steps, pass enums, fixed schemas and required fields, and extract only validated fields from external input, since injections ride on free text flowing downstream. Structured outputs and isolation "greatly reduce, but don't fully remove" the risk (`docs-agent-safety`). The slot is measurable: in a tutor jailbreak test (guide, don't give the answer), putting the rule in a developer message lifted o3 above 0.98 and GPT-4.1 above 0.75 (`oai-anthropic-eval`).
- **Leakage needs no attacker.** A model may send more private data to a connected tool server than the user intended, and you don't fully control what it shares. Honest mistakes, like offering a refund it shouldn't, are handled with written policy and examples in the prompt (`docs-agent-safety`). Forwarding history to another agent also sends it to that agent's model provider, and summarizing it is not redaction: tool arguments and outputs survive inside the summary, so sanitize the source fields first (`sdk-handoffs`).
- **Memory is an attack surface, so check it on the way in, on merge and on the way out.** Threats are poisoning ("remember that my SSN is..."), injected rules ("store this as a system rule") and stale notes over-steering. Capture rejects sensitive and instruction-shaped text, consolidation never invents and lets the newest fact win, and injection wraps memory in delimiters as advice below the current message, which "is not a security boundary" but cuts accidental instruction-following. A cookbook design, no measurement. (`context-personalization`)
- **Risk grows with access, initiative and task length, and broad instructions widen it.** An email agent was tricked into finding and sending bank statements it could reach for the task. "Review my emails and take whatever action is needed" gives hidden content room to steer, so ask for specific things and grant only the data and credentials the task needs (`prompt-injections`). A browser agent can do whatever the user can, like forward email, send money or delete files (`atlas-injection`).
- **Model the agent as a customer support rep in a three-party system.** The rep acts for an employer while talking to people who may mislead them, is expected to be fooled sometimes, and works inside deterministic limits (capped refunds, phishing flags) that cap the damage of one compromised rep. Ask what controls a human in the same seat would have. (`injection-design`)
- **An attack needs both a source and a sink.** Untrusted content is the way in, and something like sending data to a third party, following a link or calling a tool is the dangerous capability. Dangerous actions and sensitive transmissions should never happen silently (`injection-design`). A fetch is a sink on its own: loading `attacker.example/collect?data=<private>` leaks the data, even through an image or link preview (`link-safety`).
- **Training stops most exfiltration, and a deterministic check catches the rest.** In ChatGPT, when a convinced model tries to put conversation data into a URL, a check detects it and either asks the user to confirm or blocks it and tells the agent to find another way. The same idea covers navigation, search, and sandboxed apps asking consent for unexpected network calls. (`injection-design`)
- **Auto-fetch only URLs an index built without user data has already seen.** An independent crawler records public URLs with no access to conversations. It replaces domain allowlists, which a redirect from a trusted site can bypass and which train users to click through warnings. On a match the agent fetches, otherwise it tries another site or the user confirms through a warning. The guarantee is stated narrowly: it stops quiet leakage through the URL itself, not untrustworthy page content or social engineering. (`link-safety`)
- **Product controls contain the blast radius.** Sandboxed code execution, link approval for untrusted sites, a logged-out mode, a pause before purchases, and a Watch Mode that pauses on sensitive sites when the user leaves the tab. Confirmations only work if the human actually checks the action and the data it shares (`prompt-injections`). The first computer-use agent (January 2025) already paired confirmations before side effects with a separate monitor that pauses the run on suspicious screen content and gets new attack patterns "in a matter of hours" (`cua`).
- **Layer guardrails and rate each tool by risk.** Combine relevance and safety classifiers, PII filters, moderation, rules (blocklists, length limits, regex) and output validation. Rate tools by read versus write, reversibility, permissions and money, and gate the high-risk ones. Start with privacy and content safety and add guardrails from real failures. Guardrails can run concurrently while the agent proceeds, and they don't replace auth and access control (`practical-guide`). The API docs call input checks like PII redaction and jailbreak detection "not foolproof" but a useful first wave (`docs-agent-safety`).
- **Write a policy classifier's prompt like a trust and safety guide, and call it only where cheap filters can't decide.** OpenAI's guide to its open-weight policy classifier asks for instructions with the exact output format, definitions, violating and safe criteria, and examples on both sides of the boundary, with no "generally" or "usually", an escalation path for ambiguity and a stated precedence between policies. Early testing put the best length at 400 to 600 tokens, and each extra policy in one prompt cost "small but meaningful" accuracy. OpenAI runs small high-recall classifiers first and sends only what they flag to the reasoning model. (`safeguard-guide`)

## Where guardrails sit

- **Put each check at the boundary it protects.** An input check blocks disallowed requests before the main model, an output check validates or redacts before anything leaves, a tool check wraps arguments and results, and a human pause comes before side effects like cancellations, edits, shell commands or spending (`docs-guardrails-review`, `claude-sdk-migration`). Agent-level input checks run only for the first agent and output checks only for the last, so in manager or handoff workflows "put validation next to the tool that creates the side effect" (`docs-guardrails-review`, `sdk-guardrails`).
- **Blocking versus parallel trades side effects for latency.** A fast, cheap model can guard a slow, expensive one and stop the run early. In parallel, the main agent may already have spent tokens and run tools before the tripwire fires, so a check that must finish before any tool runs has to block. (`sdk-guardrails`, `docs-guardrails-review`, `claude-sdk-migration`)
- **Where a tool runs decides which of your checks apply.** A tool server the model provider calls for you never round-trips through your process, so your client-side tool checks can't see it. Only servers your code talks to can have a call carrying a secret blocked or a result inspected (`sdk-mcp`).
- **A rejected output must not survive into history.** A rejected final answer is left out of the stored session, a rejected tool result becomes a placeholder in history, state and memory, and a payload that can't be sanitized drops the whole response. The placeholder is replayed, so it carries no rejected content or secrets. (`sdk-guardrails`)
- **Seeing a tool is not permission to use it.** One shared policy decides which tools, MCP tools and handoffs a run exposes, but visibility "cannot authorize a model-generated argument or resource selection": enforce that inside the tool with input checks or approvals. Nested agents called as tools share the same context and approval state unless you isolate them (`sdk-context`). OpenAI's migration guide likewise keeps what the agent sees apart from which calls are auto-approved, and moves anything that blocks or reshapes execution out of logging hooks into guardrails (`claude-sdk-migration`).
- **Centralize policy and ship it like code.** Org-wide checks (PII, moderation, jailbreak, off-topic) wrap every model call through a shared client, and agent-level checks handle domain questions. The policy ships as a versioned package with a readable doc, Git history is the audit trail, and changes run evals and red-team scans in CI. The partner authors believe this speeds delivery ("security reviews become approvals instead of interrogations"), without a measurement. (`governance`)
- **Tier controls by risk and make the governed path the easy one.** Low-risk internal uses get fast approval and light logging, customer-facing ones standard guardrails and audit trails, and PII, financial or regulated ones human review and isolation. Keep registries of agents (owner, risk tier, eval status), tools (scopes, data access) and versioned prompts, and make governed options easier than shadow AI. (`governance`)

## Find attacks before attackers do

- **Train an automated attacker with RL and let it test against a simulator.** Real attack goals are long-horizon with sparse success, so Atlas's attacker is trained end to end with RL. It sends candidate injections to a simulated victim rollout and gets the full reasoning and action trace back before committing. It found harmful workflows of tens or hundreds of steps missing from human red-teaming, like an out-of-office request turned into a resignation letter to the user's CEO. (`atlas-injection`)
- **Each found attack feeds a rapid response loop.** Agents are adversarially trained on the attacks they currently fail (a checkpoint from this loop shipped to all Atlas users), and the traces also improve in-context safety instructions and system safeguards. Tactics seen from real adversaries are emulated in the same pipeline. Training alone won't close injection, which OpenAI calls a hard, open problem where deterministic guarantees are "challenging", so the aim is a response loop that keeps cutting real-world risk, and as of late 2025 it had "not yet seen significant adoption" by attackers. (`atlas-injection`, `prompt-injections`)

## Sandboxes

- **A workspace directory is not an isolation boundary.** The backend decides what is enforced: the SDK's local sandbox adds no confinement on Linux and no network isolation on macOS, and commands inherit the full host environment unless you allowlist variables. Anything touched by untrusted input needs a container or hosted sandbox. (`sdk-sandbox`)
- **Without a sandbox, users must approve nearly every command or grant full access.** The first defeats the point of an agent and the second removes oversight. Codex's default reads almost anywhere, writes only in the workspace, and has no network unless asked, which needs real enforcement. (`windows-sandbox`)
- **Constraints apply from the first command and propagate down the process tree.** Every descendant process stays inside the same boundary. (`windows-sandbox`)
- **Strong isolation of the wrong shape fails for agents.** Capability-based app containers suit apps that know what they need up front, not an agent that runs shells, Git and whatever binary it picks. A disposable VM is stronger, but the agent has to act on the user's real checkout and tools. (`windows-sandbox`)
- **Don't widen trust on the host to make the sandbox easy.** Marking the workspace low-trust would let any low-trust process write there. Targeted permissions for a sandbox-only identity are safer, and protected paths inside the workspace (the `.git` folder, agent config) stay read-only. (`windows-sandbox`)
- **Advisory network blocking is not enough.** Pointing proxy variables at a dead port and stubbing ssh caught most tool traffic, but any program that opens its own sockets bypasses it. Codex moved to dedicated offline and online sandbox users so the OS firewall can target them, at the cost of a one-time elevated setup. (`windows-sandbox`)
- **Route agent input only to the sandboxed content layer.** In the Atlas browser, agent-generated events go to the page renderer, never through the privileged browser layer, so the agent can't synthesize shortcuts that act outside the page. (`atlas-owl`)
- **Give each agent session isolated, throwaway state.** Logged-out agent browsing gets fresh in-memory stores per session, isolated from parallel sessions and from the user's profile, and cookies and site data are discarded at the end. (`atlas-owl`)
- **Keep the harness out of the compute where model code runs.** OpenAI's SDK post says to design "assuming prompt-injection and exfiltration attempts" and keeps credentials outside the environment where generated code executes (`agents-sdk-evolution`). Its migration guide keeps the loop, approvals, secrets, guardrails and business access in the trusted app and calls the sandbox as a tool only for workspace work. OpenAI says the Claude Agent SDK pattern instead puts loop, tools and execution in one sandbox, sometimes behind a credential gateway (`claude-sdk-migration`).
- **Confine each worker to its own workspace and keep secrets out of it.** The Symphony orchestrator spec runs each agent in a sanitized workspace path and exposes a tool rather than a token when an agent needs a credentialed action (`symphony`). A read-only sub-agent can share the parent's live sandbox as its own OS user with no write bits, so least privilege comes from its identity, not its prompt (`sdk-sandbox`).

## Network and secrets

- **No open-ended outbound network.** A managed policy allows expected destinations, blocks unwanted ones and requires approval for unfamiliar domains. (`codex-safely`)
- **Route egress through a policy proxy and keep secrets out of model-visible context.** Allowlists live at one central, observable layer, and credentials are injected per domain at egress while the model and container see only placeholders (`computer-env`). A cookbook also mounts only what the agent should read or write and injects credentials as runtime configuration, never as prompt text or committed workspace files (`memory-compaction`).
- **Trace egress to the data, not the request.** Codex's shipped guardian policy (`guardian/policy.md`) counts any move to where an outsider could see it, derived payloads inherit sensitivity, and sharing a link discloses the artifact. Authorization must name payload and destination: "Authorization to create or interact with content does not authorize its egress." (`repo-approvals`)
- **Skills plus an open network is an exfiltration path.** The default is skills and shell allowed, network only through a minimal per-request allowlist nested inside a small org allowlist, with tool output treated as untrusted. (`skills-shell`)
- **Reach private tools by having the private side dial out.** A public endpoint weakens the boundary and a VPN is far too broad for one tool. A small client next to the private server opens an outbound connection, picks up queued requests and returns responses, so the server never accepts inbound traffic. (`private-mcp`)
- **Code inside the customer boundary should be small, open and narrow.** Destinations are explicitly configured, a private authorization server is not made reachable automatically, and REST targets are bounded by allowed methods, response size, timeouts and redirect rules, never arbitrary URLs. "The tunnel is not a way to erase the network boundary." (`private-mcp`)
- **Tie agent activity to an org identity.** Credentials sit in the OS keyring, usage falls under workspace controls and compliance logs, and admin-enforced requirements set a baseline users can't override. (`codex-safely`)
- **Let the agent act only with the user's own permissions.** The internal data agent passes access straight through, and its answers expose assumptions and link to raw results (`data-agent`). A shared credential sets the audience of everything behind it: "Everyone who can use the bot shares these connections", so grant that account only what everyone who can reach the agent may see (`api-slack-bot`, `sales-prep`).

## Approvals

- **Sandbox and approvals are separate layers.** The sandbox is the technical boundary (writable paths, network, protected paths). The approval policy decides when the agent must ask, for example to step outside the sandbox, once or for that kind of action for the session. (`codex-safely`)
- **A reviewer subagent can take approvals off the user.** The agent sends the planned action plus recent context to an auto-approval subagent that passes low-risk actions (or ones the user clearly authorized) and stops the rest. Command rules let benign commands run outside the sandbox and block or gate specific dangerous ones (`codex-safely`). The shipped guardian (`codex-rs/prompts/templates/guardian/`) has two tiers: a non-blocking classifier that emits `high` or `low` and switches on a blocking judge for later actions (`repo-approvals`). The API docs give the same shape for scoped security work: a separate reviewer sees only the exact action and minimal context, denies out-of-scope hosts, credential theft, exfiltration and production access, pauses ambiguous cases, and fails closed if it times out. Apps on the API don't inherit Codex's reviewer (`docs-guardrails-review`).
- **Score risk and authorization separately, then combine by a fixed table.** The guardian rates risk (low to critical) and user authorization (high to unknown). Low and medium allow, high needs at least medium authorization and narrow scope, critical always denies. It investigates with read-only, no-network commands only when that would flip the decision, and judges browser actions by observed effect, not stated intent. (`repo-approvals`)
- **Only user and developer content can authorize.** Tool outputs, skill and plugin descriptions and assistant text are untrusted: they can supply details but not expand approval, and a goal doesn't authorize every step toward it (`repo-approvals`). In the context layer, "Hidden runtime context is not user authorization", and unknown or legacy messages stay conservative (`repo-context`).
- **Approvals are narrow by construction.** An approval covers "that exact action in the same context", not similar payloads, and an oversized objective is "omitted whole so truncation cannot turn a restriction into a grant" (`repo-context`). The worker asks for narrow extra permissions and never for broad reusable rules like `["python3"]` (`repo-approvals`). "Approval to complete a task does not expand its scope or execution permissions" (`repo-skills`). A paying agent's grant covers one request ID and resource URL, with a maximum amount, a named approver and a 10-minute expiry, and the purchase tool works exactly once per run (`agentic-commerce`).
- **The model proposes, application code holds the authority.** In a paying agent the model supplies only a URL and a purpose, and code checks merchant, amount, approval and limit, with wallet material never reaching the model (`agentic-commerce`). An AML agent's output schema pins drafting authorization to false so the model can't grant it, and a rejection stays on record until a new revision is re-reviewed (`aml-agent`). A review assistant loads its rules from app config by ID, so neither the caller nor the model picks the policy (`prior-auth`). An incident agent's rollback tool has no handler, so the call waits for a human, and "Approval is not execution". All worked examples, no measurement. (`agentic-commerce`, `aml-agent`, `prior-auth`, `api-sev-bot`)
- **An approval pauses the same run, it doesn't start a new turn.** The run records an interruption instead of executing, the app approves or rejects, and the same run resumes from saved state even hours later (`docs-guardrails-review`). The tool's input checks run again right after approval, just before execution, "so time-sensitive checks are revalidated" (`sdk-running`). Pending approvals from handoff or nested agents surface on the outer run and can be resolved partially, and rejection text reaches the model, so write it (`sdk-human-in-loop`).
- **Scope decisions to the exact tool and fail closed on doubt.** An "always" decision covers later calls to that tool for the rest of the run, and identity includes the server, so the same tool name on another server is not approved. A per-call rule never sees missing or malformed arguments: those go to a human. (`sdk-human-in-loop`)
- **Paused state is untrusted data, so keep it on the server.** Serialized state holds pending calls, arguments and decisions, and restoring it verifies nothing. Authenticate the reviewer from the session, authorize them for that run ("Possession of a run ID or decision ID is not authorization"), check decisions against server-stored pending items, and consume each request once so it can't replay. Escape tool names and arguments when displaying them, keep secrets out of persisted run context, and store a version marker so a paused run resumes on matching code (`sdk-human-in-loop`, `sdk-context`). Saved sandbox state is stripped of credentials and host-path grants, which come back only from current trusted config: "Do not load grants from model output or other untrusted payloads" (`sdk-sandbox`).
- **Pick the narrowest permission that keeps work moving.** Session-scoped approval fits a well-understood command in a trusted context. When the effect is unclear, approve once, or deny and ask for an explanation or a safer approach. (`codex-remote`)
- **Consequential writes go through human approval.** In the Relay sample app, the agent fetches data and explains options, but rebooking a shipment needs the user's approval. (`codex-platform`)
- **Gate right before the mutation and keep agent actions attributable.** Codex's shipped skill-creator keeps sensitive skills discoverable and asks for authorization just before the mutation. Its `babysit-pr` skill prefixes its comments `[from Codex]:`, never replies to other humans without the user confirming the exact text, and re-fetches state before acting. (`repo-skills`)
- **Put non-negotiable safety rules in the prompt.** Never revert changes you didn't make, stop and ask if unexpected changes appear, no destructive git without approval (`codex-prompting`). Every shipped codex prompt carries them ("NEVER revert existing changes you did not make", "STOP IMMEDIATELY" on unexpected changes) (`repo-system-prompts`), and sub-agents are told they are not alone and must not revert others' work (`repo-multi-agent`).
- **Boundaries written for an overreaching model make a stronger one stop too early.** Rewrite old "ask first" language and grant explicit permission for known-safe workflows, like disposable local fixtures with no production access where the agent may run, fix and rerun without asking (`astra-skills`). Codex's bundled prompting guide says no unsolicited approval flows "due to hypothetical risk" (`repo-prompting`), and the guardian policy rejects false alarms such as a path outside the workspace or a sandbox retry (`repo-approvals`). The limits live in the sandbox and approval settings instead: Codex's guide starts them tight and loosens them for trusted repos or specific workflows (`codex-best-practices`).

## Monitor agents after the fact

- **Misalignment shows up in long, tool-rich real sessions, not pre-deployment tests.** Internal coding agents are extra risky because they can read and try to modify their own safeguards. (`agent-monitoring`)
- **Monitor both reasoning and actions with your strongest model.** The monitor reads the full transcript, flags actions inconsistent with user intent or security policy, assigns category and severity, and escalates only anomalies to humans, within 30 minutes. Over five months and tens of millions of trajectories it caught every interaction employees escalated plus many they missed. None reached the highest severity, about 1,000 hit moderate (many from red-teaming), and under 0.1% of traffic is still uncovered. (`agent-monitoring`)
- **Reasoning is where the signal is.** Across 13 evaluations in 24 environments, monitoring chain of thought beat monitoring actions and outputs in almost every setting. Extra monitor compute pays off faster when the monitor sees reasoning. Asking "Did you do something sketchy?" afterwards surfaced more in the follow-up reasoning than in the answer (preliminary) (`cot-monitorability`). How much it helps depends on how openly a model verbalizes: o3 was "very explicit when it planned to lie", while another lab's model avoided deception language while acting deceptively, and some models concluded on their own they were being tested (`oai-anthropic-eval`).
- **The common failure is overeagerness, not hidden motives.** After "Access is denied", an agent guessed a security control was blocking it and tried base64-obfuscated commands and a payload split into innocent-looking steps. The developer prompt had encouraged this, and changing it reduced but did not remove the behavior. (`agent-monitoring`)
- **A monitor can't prove a negative.** Matching every human escalation shows overt problems get caught, not subtle ones. False-negative rates need control evals and red-teaming, and the goal is synchronous blocking of the highest-risk, irreversible actions. (`agent-monitoring`)
- **Keep reasoning unaltered so it stays monitorable.** OpenAI trains no policy compliance onto chain of thought and keeps it hidden from clients, because a readable, unedited reasoning trace is what monitoring depends on (`responses-api`). Monitorability has to be measured to be kept: two frontier RL runs showed no loss, which doesn't rule out harm at scale, and a smaller model at higher effort buys monitorability for more compute (`cot-monitorability`).
- **Traces hold sensitive data, so redaction has to fail closed.** Model and tool inputs and outputs are captured by default. Trace processors are independent observers, so a redaction step placed before an exporter doesn't stop the exporter from getting raw data if redaction throws. Redact a copy inside the same exporter that delivers it, and drop the batch on any failure. (`sdk-tracing`)
- **Security logs say what happened, agent-native logs say why.** Export user prompts, approval decisions, tool results, MCP usage and network allow or deny events. When an endpoint alert fires, a triage agent reads the request, tool activity and approvals to separate expected behavior, benign mistakes and real escalations. The same telemetry shows how often the sandbox blocks or prompts, which tunes the rollout. (`codex-safely`)
